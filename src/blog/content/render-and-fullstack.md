收到 HTML、CSS、JS 之后，剩下的活全在你浏览器里。这个过程叫渲染，分六步。

解析 HTML 成 DOM 树（骨架）；解析 CSS 成 CSSOM 树（外观）；合并成渲染树（只留要显示的）；布局（算每个元素的位置大小）；绘制（填像素）；合成（图层合并成最终画面）。逻辑跟"收到快递拆箱、看说明书、搭骨架、贴外观"一样。

DOM 树是怎么搭起来的？拿一段简单 HTML 说：浏览器遇到 `<html>` 建一个根节点，遇到 `<head>` 挂到 html 下，遇到 `<title>` 挂到 head 下，遇到 `<body>` 挂到 html 下，遇到 `<div id="main">` 挂到 body 下并记下属性，遇到 `<p>` 挂到 div 下，遇到文本"Hello, World!" 建个文本节点挂到 p 下。最终就是一棵层级树，CSS 和 JS 都靠它定位元素。这就是为什么"改一个 class 名，整页样式跟着变"——它们都绑在这棵树上。

后三步（布局/绘制/合成）值得记住一个性能常识：改几何属性（宽高、位置）会触发 reflow（重排），成本高；只改颜色这类不涉布局的属性触发 repaint（重绘），成本较低；而 transform/opacity 走合成层，几乎不卡。我优化过一个卡成幻灯片的页面，把一堆"改 top/left"的动画全换成 transform，帧率立刻从 12 飙到 60。这就是懂渲染流水线能换来的实打实的体验。

静态内容服务器直接读硬盘原样返回，快，还能被 CDN 缓存到离用户几公里的边缘节点。动态内容得现查数据库再拼。举个真实的例子：你登录电商点"我的订单"，浏览器发 `GET /my-orders`。后端从 token 里解出你的用户 ID，比如 12345，然后跑一条 SQL：

```sql
SELECT order_id, total_amount, status, created_at
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC
LIMIT 10;
```

这里的 `?` 是参数占位符，后端把它绑成 12345。关键点：别用字符串拼接（`"WHERE user_id = " + userId`），那是 SQL 注入的温床。攻击者只要把 userId 改成 `1; DROP TABLE orders;--`，拼接出来就变成两条语句，表直接没了。用占位符，数据库把 12345 当数据而不是代码，注入就失效。结果拼进模板或转成 JSON 返回，页面就有了你的订单。

我带过的人里，十个有八个第一次写的查询忘了加索引。一个 `WHERE user_id = ?` 在百万行表上全表扫描，接口要 3 秒才返回，前端显示 500 超时——他查了半天"是不是模型挂了"。加个索引，30 毫秒搞定。所以动态页面的快慢，一半在数据库，不在前端。

像 Supabase、Firebase 这类后端即服务，把整条链路砍到最简——你定义一张表加一个端点，浏览器到数据库的通路就通了。

顺着渲染流水线，有几个能直接用的优化习惯，叫"关键渲染路径（CRP）"优化：CSS 放头部尽早加载、JS 尽量延迟（defer/async）别阻塞解析、图片懒加载、首屏只加载必要资源。这些都不是玄学，都是围着"让浏览器少干点、早画出来"转。

还有个常被问的：SSR（服务端渲染）和 CSR（客户端渲染）差在哪？简单说，CSR 是浏览器拿到空 HTML 再跑 JS 画页面（首屏可能白屏一下），SSR 是服务器直接把 HTML 画好发过来（首屏快、利于 SEO）。你刷到的"首屏白屏好几秒"，多半是 CSR 项目没做好代码分割和预取。

为什么要懂这些？因为"页面卡"这种投诉，前端背锅最多，但根因可能在渲染、在网络、在数据库任何一环。你越懂全链路，越能一句话指出"问题在前端还是后端"，而不是跟着瞎改。

上面对 `?` 占位符说了原理，给你看真实的代码长啥样，省得你以为只是概念。用 Node 的 mysql2：

```js
const userId = 12345; // 从 token 解析得到
const sql = 'SELECT order_id, total_amount, status, created_at FROM orders WHERE user_id = ? ORDER BY created_at DESC LIMIT 10';
connection.query(sql, [userId], (err, results) => {
  // results 是订单数组，userId 被安全地绑定为参数
});
```

这里 `[userId]` 是参数绑定，数据库把它当纯数据，拼接注入字符串根本没机会执行。对比字符串拼接的写法 `"WHERE user_id = " + userId`——只要 userId 来自用户输入且没过滤，就是给攻击者留了后门。两条写法差一个字符，安全性天壤之别。

真遇到"页面卡"，别瞎猜，用开发者工具的 Performance 面板录一段。它会画一条时间轴，你能直接看出瓶颈在哪一环：长任务是黄的（JS 算太久）、渲染是紫的（布局重排）、网络是蓝的（请求慢）、空闲是灰的。我靠它定位过好几次"以为是前端慢、其实是某个第三方脚本在狂跑定时器"的问题。工具比直觉靠谱，这面板值得花半小时学熟。

多说一句前端框架的事。现在流行 React/Vue 这类单页应用（SPA），浏览器先拿到一个几乎空白的 HTML，再跑一大段 JS 把页面画出来。好处是交互丝滑，坏处是首屏可能"白屏几秒"——尤其 JS 包没做代码分割时。所以你会看到很多站点改回"服务端渲染（SSR）"：服务器直接把画好的 HTML 发过来，首屏秒出，SEO 也友好。这又绕回开头那句话：渲染流水线懂一点，你才知道白屏到底卡在下载、解析还是执行。

再补一个直接影响首屏的点：阻塞渲染的资源。浏览器解析 HTML 时，遇到 `<link>` 引的 CSS 会停下去下载（因为后面可能要用样式），遇到没加 `defer`/`async` 的 `<script>` 会暂停解析去执行 JS——这段等待就是白屏的来源。所以规范做法是 CSS 放 `<head>` 尽早加载、JS 尽量 `defer` 延后到解析完再跑、大图用 `loading="lazy"` 懒加载。Google 的 Core Web Vitals 就是拿这些量化的：LCP（最大内容绘制）看首屏多快、CLS（累积布局偏移）看会不会"页面突然抖一下"。我优化过一个落地页，把首屏那张 2MB 的 banner 图压缩到 200KB 并加 width/height 防抖动，LCP 从 4 秒降到 1.2 秒，跳出率直接掉了一截——调前端性能，基本就是围着这几个指标转。

前端"卡"的锅，七成不该前端背——当你能说出"卡在渲染、网络还是数据库"，你就已经超过大多数只会在控制台打印的开发者。

理解了"浏览器发请求→后端查库→返回渲染"这个循环，你就有了全栈的骨架。下一篇说一个会让你拍大腿的顿悟：你写的 API 调用和浏览器访问网页，在 HTTP 层面是同一回事。
