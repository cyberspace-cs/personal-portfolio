如果你在家用一张不错的显卡部署过 Llama 或 Qwen，大概率被毒打过：它说话像得了口吃，每蹦一个字等几百毫秒，显存还动不动就飙到接近爆满。这到底为什么？

大模型生成文字本质是自回归——一个字一个字吐，每吐一个都要看前面所有字。这个过程分两段，性质完全不同。

Prefill（预填充）：你把整段提示词丢进去，比如"写一篇推理优化的文章"。模型一次性并行算完所有字符之间的注意力关系。这是计算密集型——大量矩阵乘法，GPU 并行能力拉满，所以通常很快，耗时主要看提示词长度。像考试前快速扫教材做笔记的学生。

Decode（解码）：模型开始逐字生成。每生成一个新词，都要把前面所有历史词重新做一遍注意力计算。这里是串行的——必须等前一个词算完才能算下一个，而且历史序列每步都在变长。瓶颈不再是算力，而是数据在显存（HBM）和计算单元（SRAM）之间搬来搬去的速度。访存密集型。

为什么注意力这么吃算力？因为一次注意力要算"每个词和所有词的关系"，复杂度是 O(n²)，n 是序列长度。Prefill 时 n 是提示词长度，一次算完，摊下来快；Decode 时每生成一个新词，n 就加一，而且前面所有词的关系都要重算一遍——这就是为什么它串行又越来越慢。

一句话：卡住推理的，往往不是算得慢，而是数据在显存里搬来搬去太慢。

给你一个直观的账。在单张消费级显卡上，一个 7B 模型 Prefill 阶段能到每秒几百甚至上千 token，但 Decode 阶段常常只有 20-40 token/秒——比你打字快不了多少，所以你看着它"一个字一个字蹦"。而且提示词越长，Prefill 越慢；生成越长，Decode 越慢，因为历史越积越多。这就是为什么"长对话越聊越卡"——不是模型懒，是数学决定的。

这也能解释两个常见现象。其一，总结一篇长文时首字出来特别慢——那是 Prefill 在啃几万字，计算量集中爆发。其二，设置 max_tokens 很大但生成很短时，你多半是在浪费——模型早早说完，剩下的额度没用上。很多部署会把 max_tokens 调小来省显存。

Prefill 像站满乘客的飞机，起飞费劲但整体快；Decode 像出租车，一趟接一趟，效率极低。所有推理优化，基本都在救 Decode 这一程。

Prefill 和 Decode 的差别，还解释了两个工程现象。一是流式输出（打字机效果）：因为 Decode 是逐字生成的，服务端每算出一个 token 就立刻推给前端，前端边收边显，你才看到字一个个蹦出来——这不是 UI 特效，是底层机制决定的。二是批处理（batching）：Prefill 是并行的，所以把多个用户的提示词攒一批一起算，能大幅摊薄成本。这也为什么大模型服务商的报价常按 token 算——Prefill 和 Decode 的算力构成完全不同。

一个常见误解：调 temperature、top_p 这些采样参数会让模型变快或变慢？不会。它们只影响"从概率分布里选哪个词"，不改变计算量。真正影响速度的是模型大小、上下文长度、批大小这三样。

如果你在做应用，记住一条：尽量让提示词短而精。Prefill 成本随提示词长度线性涨，一段几千字的系统提示每次请求都要重算一遍——这就是很多"套了长 prompt 的 bot"响应慢的真凶。

Decode 为什么卡在"搬数据"而不是"算"？给你算一笔硬账。每生成一个新 token，模型都得把全部权重从显存（HBM）读进计算单元算一遍——权重是固定的，每次都要重读。一个 7B 模型半精度约 14GB，假设你的显卡 HBM 带宽是 900GB/s，那读一遍权重就要约 14/900 ≈ 0.016 秒，也就是每秒最多约 60 个 token。这就是为什么 Decode 常常只有 20-40 token/秒——它根本不是算力不够，是显存带宽这个"水管"太细，数据供不上。这也正是 KV Cache、FlashAttention 这些优化的总目标：要么少读点数据，要么让数据在靠近计算单元的地方算完。

工程上有两个指标专门描述这两个阶段：TTFT（Time To First Token，首字延迟）主要反映 Prefill 快慢——提示词越长越慢；TPS（Tokens Per Second，每秒生成数）主要反映 Decode 快慢——基本被显存带宽钉死。你评价一个推理服务"快不快"，得拆开看：用户抱怨"半天不出第一个字"，去查 Prefill/提示词长度；抱怨"吐字像蜗牛"，去查 Decode/显存带宽。把这两个数分开，你才不会乱调参数。

还有个反直觉的点：Decode 虽是串行生成，但通过批处理能大幅摊薄那次"读权重"的成本。一次读 14GB 权重，如果 batch 里同时有 32 个用户，相当于 32 个人平摊这次读取，人均成本降到 1/32——这就是高并发下服务商能把单 token 成本压到极低的原因。代价是首字延迟会略升（要等凑齐一批）。所以批大小是 Decode 阶段又一个关键旋钮，和显存、带宽一起拧。

再补一个 2024 年后很火的优化：投机解码（speculative decoding）。思路很巧：让一个小的"草稿模型"先一口气猜出接下来 4-5 个 token，再让大模型一次性验证"这几猜对不对"。猜对的部分直接采用，猜错的从分歧点重来。因为大模型验证一批 token 的成本，远低于逐个生成，整体速度能再提 2-3 倍，而且输出结果数学上和原来完全一致——相当于"让小学生先打草稿，教授只管批改"。这招在你要压榨单卡 Decode 速度时特别有用，vLLM、Ollama 都支持。它和前面的批处理不冲突：批处理解决"多人平摊读权重"，投机解码解决"单人每步多产出"，两个旋钮可以一起拧。

回头看，Decode 慢不是模型的错，是"显存带宽"这道物理天花板——你后面学的 KV Cache、FlashAttention，全是在和这堵墙较劲。

既然 Decode 这么慢，有没有办法？最直接的观察是：生成第 100 个词时，前面 99 个词的 Key/Value 其实早算好了，没必要重算。这就是 KV Cache 的由来——下一篇细讲，并顺手算一笔 Llama-2-7B 的显存账。
