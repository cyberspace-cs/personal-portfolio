优化推理有两条主线：一是压缩 KV Cache（上篇的 GQA），二是让注意力计算本身更快、更省显存。这期讲后者。

传统做法把完整 Q、K、V 从显存（HBM，大仓库）搬到计算单元（SRAM，手边工作台），算完写回。HBM 带宽远小于 SRAM，搬运才是主要耗时。FlashAttention 的核心就一句话：在哪儿干就在哪儿取料。

两个技巧。分块（Tiling）——不一次搬全部，把大矩阵切小块（比如 128×128），每次只加载一小块到 SRAM 算完再换下一块，像厨师每次只拿一块肉切，操作台始终够用。重计算（Recomputation）——它故意不存中间结果（比如 softmax 的归一化因子），反向传播时在 SRAM 上重新算一遍。看着多此一举，但因为省掉了大量 HBM 读写，整体反而更快。结果和标准实现数学完全等价，不是近似算法，能直接替换已训练好的模型。实测下来，FlashAttention 相比朴素实现，速度能快 2-4 倍，显存占用能降到 1/5 甚至 1/20，V3 还针对 H100 做了异步+FP8 优化。

为什么非得写 GPU 特化的代码？因为attention 的瓶颈不在"算"而在"搬"——SRAM 比 HBM 快一个数量级，但空间小几百倍。通用实现为了简单，把整个矩阵扔进 HBM 反复读，浪费了 SRAM 这个近水楼台。FlashAttention 就是把计算"贴着"SRAM 做，难点在于要重新设计 CUDA kernel，让分块和 online softmax 配合得天衣无缝。这也是为什么它不是改改超参就能用的，而是得换底层算子。

KV Cache 解决了"大"和"慢"，但显存碎片还在。传统做法给每个请求预分配一整块连续显存（按模型最大长度算），实际请求大多很短，60%-80% 显存白浪费。PagedAttention（vLLM 的核心）借操作系统虚拟内存思想，把 KV Cache 切成固定大小的"页"，不要求物理连续；多个请求共享同一段 prompt 时还能写时复制共享页。一个真实场景：100 个用户同时发起短对话，传统方式要给 100 人各预留最长上下文，显存瞬间爆；PagedAttention 按需分配，显存浪费趋近零，吞吐提升 2-4 倍，单机就能扛住原来需要几台机器的并发。

更粗暴但也有效的还有量化（FP16→INT8/INT4，体积缩到 1/2~1/4，KV Cache 也跟着变小）和蒸馏（大模型教小模型）。两者常叠加：先蒸馏缩小，再量化精简。一个 70B 模型量化到 INT4，体积能从 140GB 降到约 35GB，一张卡就能跑——这就是为什么你能在消费级硬件上玩"大模型"。

澄清几个误区。FlashAttention 不是银弹：当序列很短（比如几十个 token）时，分块带来的好处有限，HBM 读写本来就少，收益不明显；它真正的舞台是长序列、大模型。另外它通常不需要你手动调，HuggingFace transformers 和 vLLM 在支持的 GPU 上默认就启用，你只要别主动关掉就行。

PagedAttention 也不是孤立的，它常和 continuous batching（连续批处理）配合：不再等一个批次的所有请求都生成完才换下一批，而是哪个请求生成完立刻补一个新请求进显存页，像流水线一样转。吞吐因此能再上一个台阶。这也是为什么同样一张卡，vLLM 能比裸 transformers 多服务好几倍的并发。

如果你想动手体验：本地装个 vLLM，`vllm serve 模型名` 起一个 OpenAI 兼容的接口，拿同样的请求打过去，对比裸模型的吞吐，差距一目了然。眼见为实，比看十篇博客都管用。

给你一个直观的对比，你就知道这些优化值多少钱。同一个 Llama-2-7B，用最朴素的 HuggingFace 推理（没开 FlashAttention、没 PagedAttention、没连续批处理），单卡吞吐可能只有每秒几十个 token，且并发一高就 OOM；换成 vLLM（FlashAttention + PagedAttention + continuous batching 全开），同样一张卡能跑到每秒上千 token、并发几十路还稳如老狗。差出十几二十倍，不是模型变了，是工程细节全用上了。这也是为什么你公司里"自己部署的模型"和"大厂 API"体验差那么多——差距几乎全在这些推理引擎上。

FlashAttention 里有个容易忽略的巧思叫 online softmax。标准 softmax 得先看到整行分数才能归一化，意味着必须先算完全部再归一化，中间结果必须存回显存；online softmax 则能在分块计算时，用一组"运行中的最大值和累加和"逐步更新归一化结果，分完一块扔一块，永远不需要把整行的中间结果存在显存里。正是这个技巧，让"分块"和"不存中间结果"能同时成立——二者缺一不可，少了任何一个都省不下那笔 HBM 读写。

好消息是，这些多半不用你手写。HuggingFace transformers 在受支持的 GPU 上默认启用 FlashAttention（你只要别主动设 `attn_implementation='eager'` 关掉它）；vLLM、TensorRT-LLM 这类推理引擎更是把它们当默认底座。你的主要工作不是"实现"，而是"别关掉"和"选对引擎"。把引擎选对，比调一个月超参都管用。

容易混的一点：FlashAttention 和 PagedAttention 解决的是不同层面的问题，而且能叠着用。FlashAttention 管的是"一次注意力计算怎么更快更省"——它优化的是计算 kernel，属于单条序列内的事；PagedAttention 管的是"一堆请求的 KV 怎么在显存里摆更省"——它优化的是多请求间的显存管理。一个管"算"，一个管"存"，方向不同却不冲突。vLLM 这类引擎就是俩一起开：每条序列的注意力用 FlashAttention 加速，所有序列的 KV 用 PagedAttention 分页。理解这个分工，你就不会再问"它俩哪个更好"——答案是你两个都要。部署时 `max_num_batched_tokens` 控制一次批处理能吃多少 token，设太小吞吐上不去，设太大显存爆，也是个要拧的旋钮。我一般先按显存给个保守值，跑起来看吞吐再慢慢往上加。

把这两讲串起来：推理优化的总目标就一句——让数据少搬、让显存别碎、让计算贴着 GPU 跑，剩下的都是在这个目标下的具体招式。你之后看任何推理引擎的 benchmark，都能拿这三条去拆解它到底赢在哪。
