我在带新人时最爱问一个问题：你写了这么多年前端，有没有想过 `fetch('/api/users')` 和浏览器打开一个网页，底层是同一件事？大部分人愣一下。

浏览器访问网页，发出 `GET /index.html`，服务器回 index.html（一种文本）。前端调 API，发出 `GET /api/users`，服务器回 `[{"name":"Alice"}]`（JSON，另一种文本）。从 HTTP 看，机制完全相同——都是请求-响应，区别只在返回格式：HTML 交给渲染引擎画页面，JSON 交给 JS 逻辑当数据。

这就是为什么"全栈"这词合理。你一旦看懂一次浏览器请求的完整过程，后端 API 的核心原理你也就懂了——根本没有"两种请求"，只有一种 HTTP 请求、返回格式不同。所谓"前端工程师"和"后端工程师"的分工，更多是团队组织上的便利，不是技术上的天堑。

新人常犯的错，是把 API 当魔法。我带过一个人，他的页面调 `/api/orders` 一直返回 500，他就只会点重试，重试十几次还是 500，然后跑来问我"模型是不是挂了"。我让他查后端日志，发现是那条 SQL 少加了个索引，查询超时。他卡了两天的问题，懂了"请求→查库→返回"这条链路后，十分钟就定位了。你看，顿悟不是知识增量，是视角切换。

光说不够，带你写一个真实的接口感受一下。用 Node 的 Express，五行业务代码就能起一个能查库的 API：

```js
app.get('/api/orders', async (req, res) => {
  const userId = req.auth.userId;            // 从 token 解出用户
  const rows = await db.query(                // 查数据库
    'SELECT * FROM orders WHERE user_id = ?', [userId]);
  res.json(rows);                            // 返回 JSON
});
```

前端那边 `fetch('/api/orders')` 拿到 `rows`，渲染成列表——和浏览器拿 HTML 渲染页面，是同一套"请求→处理→返回"的循环，只是返回的是数据不是文档。你前脚写前端、后脚写后端，中间没有不可逾越的墙。

一个常见的小坑是 CORS：前端在 a.com、接口在 b.com 时，浏览器会拦截跨域响应，报一大串红字。这不是接口坏了，是浏览器的安全策略要求 b.com 显式声明"允许 a.com 访问"。懂了 HTTP 这套，你就不会被这种报错吓住。

第一章说的"编程语言变成自然语言"，到这儿就落地了。当你用说话的方式指挥 AI 写代码，你其实是在指挥一次"网络快递"正确流转：请求发到哪、返回什么、怎么拼回页面。理解这套底层，你才能判断 AI 生成的接口靠不靠谱——它返回的字段对吗？会不会多查一次库？你不是在写每一行，你是在当调度员。

顺手补几个接口常识。第一，API 通常要做版本化，比如 `/api/v1/orders`，这样你改接口时老用户不会被坑。第二，REST 和 GraphQL 之争一句话带过：REST 用不同 URL 表达资源，GraphQL 用一个端点让你自己声明要什么字段——后者在"前端要的字段经常变"的场景更省事，但缓存和限速更复杂。第三，测接口别只会点页面，学会用 `curl` 或 Postman 直接打，能绕开前端 bug 单独验后端。

vibe coding 实战里这特别有用：你可以让 AI"写一个 /api/v1/orders 的 GET 接口，从 orders 表按 user_id 查最近十条"。它生成的代码对不对，你用 curl 一打就知道——返回的是不是 JSON、字段对不对、有没有 500。把"看页面"换成"打接口"，你的调试效率会翻倍。

这一篇的顿悟，建议你合上屏幕自己复述一遍：浏览器访问网页和调 API，底层是不是同一回事？能讲清楚，网络这块就算入门了。

光看后端不够，给你看前端怎么消费这个接口。在浏览器里，你写的其实就是：

```js
const res = await fetch('/api/orders');
const orders = await res.json();   // 把返回的 JSON 变成 JS 对象
renderList(orders);                // 交给渲染逻辑画成列表
```

`fetch` 发出去的 HTTP 请求，和浏览器地址栏敲 URL 发出的，底层完全相同——只是这次返回的是 JSON 而不是 HTML，接收方从"渲染引擎"换成了"你的 JS 代码"。理解这点，你就不会再把"前端"和"后端"当成两个不相干的世界。

这个顿悟在 AI 时代尤其值钱。你调 OpenAI、DeepSeek 的接口，本质也是一次 `fetch`：POST 到 `/v1/chat/completions`，body 里带 prompt，服务器回一段 JSON（含模型生成的文本）。它和上面那个 `/api/orders` 没有任何本质区别——都是"发请求、收 JSON、在代码里处理"。所以你前面建立的网络直觉，直接能迁移到 AI 应用开发：AI 接口偶发超时？去看 TCP/HTTP；返回 429？限流；有时候慢？可能是服务端 Prefill 在啃长 prompt（下一篇就讲）。网络这块打通了，后面学 AI 工程会顺很多。

再给个实用习惯：调试接口永远先甩开前端。`curl https://你的域名/api/orders` 直接在终端打，能看到最原始的状态码和返回体。如果 curl 正常但页面报错，问题在前端；如果 curl 就 500，问题在后端或数据库——这一步能帮你把"到底是哪出了问题"的排查范围砍掉一半。我带的人里，会用 curl 隔离问题的，定位速度普遍快三倍。

既然是同一套 HTTP，顺手把写 API 的规矩说清，省得你以后踩坑。资源用名词不用动词：用 `/users` 而不是 `/getUsers`，用 HTTP 方法（GET/POST/PUT/DELETE）表达动作。状态码也别只会 200 和 500：创建成功回 201 Created，删除成功回 204 No Content，参数校验没过回 422 Unprocessable Entity，认证失败回 401。请求参数也有讲究：过滤/分页用查询参数（`/orders?status=paid&page=2`），定位某个资源用路径参数（`/orders/12345`）。这些约定不是死板，是让前后端、甚至不同团队之间不用每次重新对齐语言。我接手过一个"人人自创状态码"的项目，前端每个接口都要 special-case，维护起来苦不堪言——统一约定省下的沟通成本，远超你想象。

把这个顿悟刻进肌肉记忆：你写的每一个 fetch、调的每一个接口、甚至和 LLM 的对话，都是同一条 HTTP 请求换了个返回格式。我带新人时，这一步讲通了，后面学任何后端框架都快一倍——因为底层那根线，他们已经拿住了。
