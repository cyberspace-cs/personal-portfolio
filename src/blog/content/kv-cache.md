上篇留了个问题：生成第 100 个词时，前面 99 个词的 Key/Value 早算好了，凭什么重算？KV Cache 就是把这些算过的 Key、Value 存起来，下次直接用。

先快速复习注意力：每个词在注意力层生成 Query（问谁跟我相关）、Key（我有什么特征）、Value（要提取的信息）。解码时新词要和前面每个词的 Key、Value 匹配——而这些前面早算好了，只是没存。KV Cache 把它们贴上"桌面"，查的时候直接看，不用翻旧文档。

这一存，解码每步计算量从 O(n²) 降到 O(n)。但"桌面"（显存）越来越小。想象你边工作边把每一条笔记都贴满整面墙，墙迟早贴满——长文本越聊越慢、显存动不动爆（OOM），根子在这。

拿 Llama-2-7B 算一笔实在的账。它有 32 个注意力头，半精度（float16，每参数 2 字节）。序列长度 4096、批大小 1 时，光 KV Cache 就要约 2GB 显存，而模型权重本身才 14GB 左右。对话变长、或同时服务多个用户（批大小变大），KV Cache 按 O(批大小×序列长度) 线性涨，很快超过权重，成显存头号杀手。

我第一次本地跑 13B 模型时就栽在这：显存标称 24GB，我以为权重装不下是卡不行。后来才懂，就算权重装得下（13B 半精度约 26GB，确实装不下——但这里先假设装下了），长上下文的 KV Cache 也会把剩余显存吃光。所以"模型能装进显存"和"能跑长对话"是两回事——很多人卡在后者还不知道为什么，只能纳闷"怎么才聊二十轮就 OOM"。

批大小的影响特别容易被低估。批大小从 1 涨到 32，KV Cache 直接翻 32 倍——这就是为什么一个看起来能跑的模型，一旦上生产要并发服务几十个用户，显存立刻崩。做推理服务的人，大半精力都花在"在显存上限内塞下更多并发"上。

不能光靠堆显存。DeepSeek-V2 的 MLA 对 Key/Value 做低秩压缩，把每 token 的 KV 大小压到约 d 级别；GQA 让几个头共用一组 K/V（下篇细说）。同等预算下能撑更长的上下文或更大的批。到 2026 年，KV Cache 优化已经从"可选项"变成"标配"——开源模型规模越大，这一点越致命。

如果你自己部署，有几个立竿见影的省显存招：用 GQA 架构的模型（同样参数量 KV 小几倍）、把上下文窗口设短一点、量化到 INT4（KV 也跟着缩）、或者干脆上 vLLM 这类带 PagedAttention 的引擎（下下篇讲）。

多轮对话是怎么吃显存的？每一轮你发的消息、模型回的每句话，都变成 KV 存进缓存，且整个对话历史是持续累加的——对话越长，KV 越大，直到撞显存上限被截断（这就是"上下文窗口"的硬限制）。所以"忘掉前面内容"在技术上不是模型记性差，是显存装不下了。

工程上有几个救法。前缀缓存（prefix caching）：系统提示词每次都一样，它的 KV 算一次缓存起来复用，不用每轮重算，能省下不少 Prefill。滑动窗口：只保留最近 N 轮，丢掉更早的 KV——代价是模型可能"忘了"开头说的事。这些都是在"记性"和"显存"之间做权衡。

怎么知道你的服务 KV 吃紧？vLLM 这类引擎会暴露 metrics，你能看到每请求的 KV 占用、缓存命中率。我第一次看这些指标时才真正"看见"了显存去哪——之前全是黑箱猜。做推理服务，观测比拍脑袋重要得多。

KV Cache 还解释了另一个你常听到的词："上下文窗口"。所谓 4K、32K、128K 的上下文，本质就是 KV Cache 能容纳的 token 数上限——窗口越大，单条对话占的显存越多，同一张卡能并发的用户就越少。所以"支持 128K 上下文"和"能同时服务 100 个用户"往往是鱼与熊掌：你给单用户开 128K，显存就不够再开第二个。很多服务商会默认把上下文窗口设小、按需放大，就是在"长对话"和"高并发"之间找平衡点。

我做过一个长文档问答的活，用户传了个 200 页的 PDF，聊到一半模型突然"失忆"，前言不搭后语。查了一圈才发现，是上下文窗口被 KV Cache 顶满，最早的对话历史被默默截断丢弃了——模型不是记性差，是显存真装不下了。解决法是把长文档做向量检索，每次只把最相关的几段塞进 prompt，而不是全盘塞进去。这也是 RAG（检索增强生成）为什么流行的底层原因：它绕开了 KV Cache 的长度天花板。

还有个省显存的连带效果：你量化模型（FP16→INT4）时，KV Cache 也跟着缩。因为 Key/Value 同样是浮点，精度降了，存的字节数就少。所以"量化"这招是一箭双雕——权重和 KV 一起变小，显存立刻宽松。小模型能跑在消费级显卡上，一半功劳在量化，另一半在 GQA 这类架构优化。

给你个能直接拿来估显存的账。假设用 GQA 模型（每 token KV 约 0.25MB，像上篇算的），序列长度 4096、批大小 32：KV 总占用 ≈ 0.25MB × 4096 × 32 ≈ 32GB——光 KV 就吃掉一张 4090(24GB) 的全部显存还不止。这就是为什么"并发 32 路"对消费级显卡是奢望：权重 14GB 加上这 32GB KV，得 46GB 往上，非得 80GB 的 A100/H100 不可。所以部署时 `max_num_seqs`（最大并发序列数）和 `max_model_len`（最大上下文）是两个要一起拧的旋钮——把并发调小或上下文调短，KV 立刻松绑。vLLM 的 `--gpu-memory-utilization` 就是控制留给 KV 的比例，默认 0.9，显存紧时调到 0.8 能让它更早拒绝新请求而不是 OOM。很多新手只盯着"模型多大"，却栽在"并发和长度攒出来的 KV"上。

一句话收尾：KV Cache 是推理服务的显存账房，你每多开一轮对话、每多并发一个用户，都在往这个账房里存一笔，得时刻盯着它别爆。这也是为什么很多推理服务要设 max_tokens 上限和会话超时——本质都是在给这个账房设止损线。

KV Cache 的本质是用显存换计算——它绕开了算力瓶颈，却撞上显存天花板。下一期看注意力头本身怎么"瘦身"：MHA、MQA、GQA 的显存博弈。
