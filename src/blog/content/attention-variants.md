KV Cache 这么占地方，能不能直接给它瘦身？得从多头注意力的源头说起。

MHA（标准多头）：每个注意力头独立拥有自己的 Query、Key、Value。KV Cache 每头一份，独立存。最细最全，但本子堆满柜子，占地方。

MQA（多查询）：激进思路——所有头共享同一组 Key、Value，只保留独立的 Query。相当于全班共用一本笔记，省到极致。代价是每个人记录的细节可能丢失，精细任务上精度容易掉。

GQA（分组查询）：折中方案，不打乱而是分组：比如每 4 个 Query 头共享一组 K/V。像每 4 人合一本笔记，既大大省空间，又因共享范围有限保留了足够细节。

先给你一个能直接算的账。KV Cache 每 token 的大小 ≈ 2 × 层数 × 每头维度 × 头数 × 2字节（K 和 V 各一份）。对 Llama-2-7B（32 层、32 头、每头维度 128）：MHA 下每 token KV 约 2×32×128×32×2 ≈ 0.5MB；序列 4096 就是约 2GB——跟上篇对上了。换成 GQA（8 组共享），头数那项直接除以 8，KV 降到约 0.25MB/token，同样的 4096 序列只要约 0.25GB。这就是 GQA 的杀伤力：同样显存，上下文长度或并发数能翻几倍。

为什么 GQA 成了标配？拿数字说话。Llama-2-70B 在 MHA 下，KV Cache 轻松吃上百 GB，单张消费级显卡根本装不下，只能靠多卡或量化硬扛。换成 GQA（每组 8 个头共享）后，KV 显存直接降到约 1/8，同样一张卡能扛的并发用户数或上下文长度翻了好几倍。它是 MHA 的质量和 MQA 的效率之间最划算的那一点，所以现在开源大模型大多默认 GQA——Llama-2-70B、Llama-3 全系、Qwen2 都是。

MQA 为什么没人敢随便用？有个真实教训：在需要精细指代消歧的任务上（比如"把左边第二个盒子的盖子打开"这种多物体指令），MQA 因为共享 K/V，常常分不清"第二个"指的是谁，成功率比 MHA 掉一截。GQA 把共享范围限制在组内，既省钱又没那么糙，这才被工业界普遍接受。

对你选模型的实在建议：如果你显存紧张又想跑长上下文，优先挑 GQA 架构的模型（现在主流都已经是了）；如果你在做对精度极度敏感的任务，注意小模型用激进 MQA 的可能掉点；量化时 GQA 模型的 KV 也会按比例缩小，省显存最划算。

给了账，再给点实操。想知道一个模型的注意力配置？去它的 `config.json` 看 `num_attention_heads`（总头数）和 `num_key_value_heads`（KV 头数）。两者相等就是 MHA；后者是前者的约数（比如 1/8）就是 GQA；后者是 1 就是 MQA。现在开源主流基本都是 GQA，看一眼就知道它省不省显存。

MLA 和 GQA 谁更省？DeepSeek-V2/V3 用的 MLA（低秩压缩）比 GQA 更激进，KV 能压到更小，这也是 DeepSeek 能在同等显存下撑超长上下文的底气。不过 MLA 实现更复杂，需要框架专门支持，不是随便换模型就能享用的。

推理服务里的真实取舍：MQA 虽然精度略掉，但吞吐极高，所以在"要扛海量并发、精度要求没那么苛刻"的场景（比如某些摘要、分类服务）仍有用武之地。GQA 是精度和吞吐的最大公约数，所以成了默认。没有最好的，只有最适合你场景的。

把三者摆一起看更清楚：

- MHA：每头独立 K/V，质量最高、最占显存。适合对精度极度敏感、且显存充足的场景（比如某些云端大模型推理）。
- MQA：所有头共享一组 K/V，显存最小、吞吐最高，但精细任务易掉点。适合"要扛海量并发、精度要求宽松"的服务（摘要、分类、embedding）。
- GQA：分组共享，质量和效率的最大公约数。2023 年后新模型几乎默认它——Llama-2-70B、Llama-3 全系、Qwen2、Mistral 都是。

没有永远最好的，只有最适合你场景的。

顺带一个选模型时的实战细节。你看模型卡片写"70B"，别默认它显存友好——先查它的 `num_key_value_heads`。如果它仍是 MHA（KV 头数 = 总头数），那 KV Cache 轻松上百 GB，单卡根本跑不了，必须多卡或量化；如果是 GQA（KV 头数远小于总头数），同样 70B 可能单张 80GB 卡就能跑长上下文。我帮人选型时，第一眼就看这个字段——它比参数总量更能预示你部署时要花多少显存。

再说透一点 MLA（DeepSeek 用的低秩压缩）。传统 KV 存的是每个头的完整 Key/Value 向量；MLA 把 Key/Value 先压缩成一个更小的"潜向量"存着，用的时候再解压还原。相当于不存原始笔记，只存笔记的摘要，要用时展开。这样每 token 的 KV 能压到原来的几分之一甚至更少——这正是 DeepSeek 能在同等显卡下撑起超长上下文、还保持低价的原因。代价是实现复杂，需要推理框架专门适配，不是换个模型文件就能享用的。

把这三个变体的来龙去脉理一下，你会更懂为什么现在默认 GQA。2017 年 Transformer 诞生时用的是 MHA（每头独立 K/V），质量好但没人觉得 KV 会成问题；2019 年 MQA 提出，为了省显存极致共享 K/V，但精度掉得明显，没普及；直到 2023 年 GQA 出来取了中间值，才被 Llama-2、Mistral 等纷纷采用，成了事实标准。所以"MHA→MQA→GQA"不是谁取代谁，而是在"精度"和"显存"之间反复找平衡点，最后 GQA 胜出。这也是为什么现在新发布的开源模型几乎清一色 GQA——不是巧合，是踩过坑后的共识。

落到你选模型：如果你只有一张 24GB 的 4090，优先挑 GQA 的 7B-14B 模型（如 Qwen2-7B、Llama-3-8B），长上下文和并发都更从容；想上 70B 级，基本得靠 GQA + 量化 + 多卡，单卡跑不动 MHA 版本的 70B。先看一眼 `num_key_value_heads`，比看参数总量更管用。

选模型时把它当铁律：先看 num_key_value_heads，再决定你的显卡够不够——这一步能帮你避开 90% 的"部署翻车"。记住，模型参数量只是故事的一半，另一半是它怎么存 KV——后者才决定你兜里的显卡能不能跑起来。

压缩 KV Cache 是一条路，另一条路是让注意力"算得更快、搬得更少"。下期讲 FlashAttention 的分块黑魔法，和 vLLM 的 PagedAttention 怎么把显存碎片利用到趋近零。
