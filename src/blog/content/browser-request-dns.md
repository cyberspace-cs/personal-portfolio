我习惯把所有网络问题都还原成一句话。浏览器请求网页，其实就是一次网购。

你在地址栏敲 `https://example.com/shop/item?id=123`。浏览器先把这串"订单"拆开——协议(https)告诉它用哪种快递；域名(example.com)是收件人小名，电脑不认；路径(/shop/item)是去哪个货架；参数(?id=123)是商品编号。这一步就是个文本拆分，没什么神秘的。

电脑只认 IP，比如 `93.184.216.34`。域名就是小名，IP 才是身份证。所以浏览器得查"电话本"，也就是 DNS。查的路径一般是：先看本机缓存和 hosts 文件，再问本地 DNS 服务器，一层层往上，直到找到管 example.com 的权威服务器。

递归和迭代的区别，是很多人一直没搞清的点。拿 example.com 举个完整的递归例子：你（浏览器）问本地 DNS "example.com 的 IP 是多少"；本地服务器不知道，去问根服务器；根说"去问 .com"；本地再去问 .com 服务器；.com 说"去问 example.com 的权威服务器 ns1.example.com"；本地最后问 ns1，权威回答"是 93.184.216.34"，本地把结果带回给你。整个过程你只发了一次请求。迭代查询则是每一级只告诉你"下一站去哪"——本地 DNS 自己一级级追，每次都被"踢皮球"，直到找到答案。实际运作里，你电脑通常只用递归找本地服务器，后面怎么查是它的事；而根、顶级域、权威服务器只做迭代回复。这个分工，让几十亿台设备能在一秒内查到域名真正的 IP。

一个真实的坑：把域名拼错一个字母，比如 exmaple.com，DNS 会返回 NXDOMAIN（域名不存在），浏览器直接报"无法访问"。很多人以为是网络坏了，其实只是手滑。理解 DNS 链路，你一眼就能定位是"域名解析不了"还是"服务器没响应"——这两种故障的排查路径完全不同。

想自己观察 DNS 怎么工作？在终端敲 `dig +trace example.com`，你能看到从根到权威的完整追问链条，和上面讲的一模一样。这是我觉得最值得亲手跑一次的网络命令，比看十篇博客都直观。

传统 DNS 是明文出行的——中间谁偷听，都知道你访问了哪个站。这催生了几个补救方案，怎么选看场景：
- DoH 把 DNS 查询伪装成普通 HTTPS 流量走 443 端口，混在网页请求里，防火墙很难单独拦，适合被运营商劫持严重的网络。
- DoT 用专门 853 端口建独立加密通道，更标准，但端口容易被识别阻断。
- DoQ 基于 QUIC，省掉 TCP+TLS 两次握手，弱网下更有优势。

到 2026 年，DoH 已是主流浏览器的默认选项之一；如果你在意隐私，手动开 DoH 是最低成本的一件事。顺便提一句，大网站背后往往还有 CDN 和 Anycast——你查到的 IP 不一定是"源头"，而是离你最近的那台边缘节点，这也是为什么同样的域名，北京和纽约解析出的 IP 不一样。

再说两个 DNS 的真实坑。其一，改了域名解析却不生效——多半是 TTL（生存时间）没过期，本地和各级 DNS 还缓存着旧 IP，只能等几分钟到几小时。所以改 DNS 前先看 TTL，紧急时把 TTL 先调小再改。其二，有时你 ping 得通一个域名、网页却打不开——ping 通只说明网络层和 DNS 通了，不代表对方 80/443 端口的服务在跑，得用 `curl -v https://域名` 看应用层。

本地调试还有个老把式：改 hosts 文件把某个域名绑到自己电脑的 IP，就能在不上线的情况下用真实域名测前端。我们团队每次联调都这么干，比改代码里的地址靠谱。

最后提一句 Anycast：大站点往往在全球几十个节点都宣告同一个 IP，你的请求会被路由到最近的健康节点。所以同样的域名，北京和纽约解析出的 IP 不同，这很正常，不是 DNS 抽风。

把迭代查询的完整链条单独拎出来，你会更清楚"踢皮球"长什么样。本地 DNS 问根服务器"example.com 在哪"；根回"我不知道，但 .com 的服务器是 a.gtld-servers.net"；本地再去问 a.gtld-servers.net；.com 回"去问 example.com 的权威服务器 ns1.example.com"；本地最后问 ns1.example.com；权威才给出真正的 IP。注意每一步对方都只给"下一站地址"，从不多走一步——这就是迭代。递归和迭代的分工很妙：你只跟本地服务器打交道（它替你递归），而根、顶级域、权威永远只做迭代，谁也不替谁跑完全程。全球几十亿设备能在一秒内解析域名，靠的就是这套分层接力。

还有一个中国特色的坑：运营商 DNS 劫持。有些宽带会在你访问不存在的域名时，把页面跳转到它的广告站，或者把某些域名解析到错误 IP。普通 DoH 能防偷听，但防不了"本地 DNS 服务器本身被运营商动了手脚"——这时候大厂 App 会直接用 HTTPDNS：跳过系统 DNS，直接拿一个 HTTPS 接口问自家的解析服务要 IP。这也是为什么你手机上的淘宝很少遇到"网页被劫持"，而浏览器偶尔会。

学会读 `dig` 的输出也值回票价。它回的 ANSWER SECTION 是最终 IP，AUTHORITY SECTION 是权威服务器，ADDITIONAL 里有时带 glue 记录。当你怀疑"解析到了错误 IP"，`dig @8.8.8.8 example.com` 强制用谷歌的解析器查一次，能立刻判断是"本地 DNS 被改了"还是"域名本身配错了"——这是定位 DNS 故障最快的一招。

落到能动手的事：想真正用上 DoH，不需要换浏览器。Chrome/Edge 在设置里搜"安全 DNS"就能选 Cloudflare(1.1.1.1) 或 Google(8.8.8.8) 的加密解析；系统层也可以在网卡配置里直接填这两个 DNS，全机所有流量都走加密查询。我做前端联调时习惯把本机 DNS 指向 1.1.1.1，既快又避开了本地运营商的小动作。改完记得 `ipconfig /flushdns`（Win）或 `sudo dscacheutil -flushcache`（Mac）清掉旧缓存，不然可能还命中之前的错误记录——很多人"改了 DNS 没生效"，其实就是没清缓存。

排查网络问题有个铁律：先分层定位——物理层通不通、DNS 解没解、应用层在不在跑，一层层剥，别一上来就重装系统或换路由器。

域名只是入口。下一篇讲清楚：浏览器拿到 IP 后，怎么确认对方"营业中且愿意接单"——也就是 TCP 三次握手，以及为什么它非得是三次。
