网络协议里我觉得最精妙的设计之一，就是 TCP 三次握手。第一次学的时候我也纳闷：两次不行吗，非得三次？

假设浏览器初始序列号 ISN 是 x，服务器是 y。

第一次 SYN：浏览器发"你好，营业吗？我准备发货，编号 x"。

第二次 SYN-ACK：服务器回"营业中，收到你的 x 了，期待你发 x+1；我也准备好了，我的编号 y"。

第三次 ACK：浏览器回"收到你的 y 了，开始送货，编号 x+1"。

关键在确认号：每回的 ack 都是对方 seq+1，证明"我确实收到了你上一条"。这就像两个人核对快递单号，每收一件都回执"收到第 x 件了，等第 x+1 件"。

如果只握两次——浏览器发 SYN，服务器回 SYN-ACK 就当连接建好了——麻烦来了。网络有延迟和重传，一个早就过期的旧 SYN 包可能迟到了，服务器一看"哦新连接"，直接开干，结果两端状态对不上，白建一条连接还浪费资源。三次握手强制双方都确认"对方能收也能发"，才敢传数据。

顺带一提，初始序列号 ISN 是随机生成的，不是从 1 开始。原因很实际：如果 ISN 可预测，攻击者能伪造一个"旧连接的残留包"插进来——这就是经典的 SYN flood 攻击的温床。随机 ISN 让伪造包难以蒙混过关。安全设计往往就藏在这种细节里。

我调试过最久的一个 bug 就跟握手有关。一个内部服务偶尔连不上数据库，报错"connection refused"，但数据库进程明明在跑。最后发现是中间那层防火墙把 SYN 包当成了"可疑扫描"给丢了——客户端发了 SYN 石沉大海，三次握手永远走不完，表现就是连接超时。看懂握手流程，你才知道该去查"包有没有到对端"，而不是对着应用代码发呆。

还有两种常见失败：对端端口没监听，握手会收到 RST（重置），表现为"connection refused"；网络彻底不通，客户端等不到 SYN-ACK 就超时，表现为"timeout"。光看报错就能猜个八九不离十，这就是懂协议的价值。

这套相互确认有开销，所以有了 HTTP Keep-Alive——一个连接处理多次请求，不用每次都重新握手。没有它，一个 80 资源的页面要握 80 次手，光握手就够你喝一壶。你可以在浏览器开发者工具的 Network 面板里看到：同域名的请求大多复用同一条连接（Connection ID 相同），这就是 Keep-Alive 在起作用。

顺带把 HTTPS 的账也算上。我们说的三次握手只是 TCP 层，如果是 https，握手之后还要再来一轮 TLS 握手（协商密钥、验证书），又是几次往返。所以建一条加密连接比明文慢不少——这也是为什么 HTTP/3 要把 TCP 和 TLS 握手合并来救延迟。

想亲眼看握手？装个 Wireshark，过滤 `tcp.flags.syn==1`，你能抓到浏览器发出的 SYN、服务器的 SYN-ACK、客户端的 ACK 三步，和本文讲的一字不差。我刚学网络时靠这招把抽象的协议变成了屏幕上的真实包，理解深度完全不一样。

还有个工程常识：操作系统对单进程能开的连接数、对 TIME_WAIT 状态的回收都有上限。高并发服务偶发的"连接数爆了"，根子常常不在代码，而在这些内核参数。懂了握手，你才知道该去调 `ulimit` 还是 `net.ipv4.tcp_tw_reuse`。

顺带提一句连接的结束。握手是三次，挥手是四次（FIN/ACK/FIN/ACK）——因为 TCP 是全双工的，关闭时两边要各自确认"我没数据要发了"。你有时会看到连接卡在 FIN_WAIT2 或 TIME_WAIT，多半是某一端没好好发最后的 ACK，常见于代码里忘了关连接。

一个排查口诀送你：连不上先看握手（SYN 有没有到对端），通了但慢看吞吐（是不是队头阻塞），偶发失败看 RST（是不是被防火墙或限流掐了）。这三句覆盖了八成网络故障。

三次握手还有个绕不开的安全话题：SYN flood 攻击。攻击者伪造大量源头 IP 发 SYN，服务器为每条连接预留资源、进入半连接队列等待 ACK，队列被填满后，正常用户的 SYN 也被丢弃，连接怎么都建不上。防御的一招是 SYN cookie：服务器不提前分配资源，而是把连接信息编码进回包的序列号里，等真正收到 ACK 时再还原——相当于"不记笔记，把答案写在本子上带回来的那张纸背面"。Linux 默认开着 `net.ipv4.tcp_syncookies`，就是这个用意。

还有个工程上常被忽略的点：半连接和全连接队列（backlog）。服务器收到 SYN 后，连接先挂进半连接队列；完成三次握手后移入全连接队列，等 `accept()` 取走。如果你的应用处理慢、来不及 accept，全连接队列塞满，新握手就会被悄悄丢掉，表现就是"偶发连不上、重试就好"。调大 `net.core.somaxconn` 和应用的 listen backlog 能缓解，但根子还是得让服务端处理得更快。

我踩过最典型的连接相关问题不是握手失败，而是"连接数爆了"。一个高并发服务跑一阵后开始大量报 connection refused，查代码没 bug，最后发现是单进程默认只能开 1024 个文件描述符（Linux 的 `ulimit -n`），连接本质也是文件描述符，用光了就再也建不了新连接。把 `ulimit -n` 调大、再配合连接池复用，问题才消。这种坑你光看应用层永远找不到，得知道连接背后站着操作系统。

想自己看连接处在哪个状态？别只靠 Wireshark。Linux 上 `ss -tnp` 能列出所有 TCP 连接和它的状态：ESTABLISHED 是建好的，SYN_SENT 是一直等不到回包（多半网络不通或防火墙丢 SYN），TIME_WAIT 是一堆关不掉的"残影"。高并发服务偶尔抽风，一查 `ss` 满屏 TIME_WAIT，就是连接没好好关闭、端口被占着释放不掉。临时解法是开 `net.ipv4.tcp_tw_reuse` 让系统复用这些端口，但治本还是得让代码规范地关连接——很多"偶发连不上"的灵异事件，根子都在这里。

我常跟人说：网络故障八成在握手和防火墙，先把 SYN 看明白了，再去怪应用代码。
