---

## 1. 背景与问题

代码审查阶段将「错误回显可能泄露内部信息」标记为 R5（一般项，信息泄露风险低）。当前后端依赖 FastAPI 默认异常处理：

- 生产环境 `debug=False` 时，FastAPI 对未捕获异常默认返回 `{"detail":"Internal Server Error"}`，**不**向客户端回显堆栈；
- 但缺少**显式的统一异常处理层**，存在两点隐患：
  1. 若未来误开 `debug`，堆栈将直接泄露路径/SQL/配置；
  2. 各错误响应形态不统一，不利于前端统一拦截与用户体验一致。

本迭代目标：**建立显式、统一的异常处理层**，对客户端只暴露安全的错误文案，内部细节仅记录在服务端日志。

## 3. 功能设计

### 3.1 全局异常处理器（核心）
- 注册 `app.add_exception_handler(Exception, _unhandled_handler)`：捕获所有未处理异常。
- 行为：
  - 服务端：通过 `logging` 记录完整异常与堆栈（`logger.exception`）。
  - 客户端：固定返回 `HTTP 500` + `{"detail": "服务器内部错误，请稍后重试"}`，**绝不**序列化异常原文。

### 3.2 一致性信封（HTTPException）
- FastAPI 的 `HTTPException` 默认即以 `{"detail": <message>}` 返回，本迭代**保留**该行为，不改动 401/404/422 的既有语义，仅确认其不泄露内部信息（本项目自建 `HTTPException(detail=...)` 均为安全文案）。
- 不拦截 `RequestValidationError`（422），保留字段级校验信息以便前端定位——此为预期 UX，非泄露。

### 3.3 配置约束
- 明确生产以 `debug=False` 运行（`.env` / 部署配置），从根上杜绝堆栈外泄。

---

## 4. 非功能要求
- 性能：异常处理为低频路径，无额外开销。
- 安全：客户端响应零内部信息；日志含敏感上下文但仅落本地/集中日志，不出网。
- 兼容：不改变既有成功路径与 401/404/422 状态码。

## 5. 验收标准（DoD）
- [ ] 未捕获异常返回 500 + 通用文案，响应体不含异常类型/路径/堆栈。
- [ ] 服务端日志打印完整 traceback。
- [ ] 401/404/422 行为不变，结构统一为 `{"detail": ...}`。
- [ ] 自动化测试覆盖上述三点。
