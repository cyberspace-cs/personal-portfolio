## A. 技术深挖（必考题，按"是什么→为什么→本项目怎么做的→取舍"组织）

### A1. 讲讲你这个项目的整体架构
- 要点：分层（API/编排/服务/模型）、Agent 编排主链路、可插拔 LLM、检索与 OA 适配层；
  一句话带出"动作自动化 + 可溯源 + 成本可控"三条主线。

### A2. 为什么用 Agent 而不是直接 RAG/ chatbot？
- 要点：用户一句话常含**多意图多动作**（借终端+开视频会+联网），需要**规划/拆单/路由/记忆**；
  RAG 只解决"问答"，Agent 解决"把事办成"。本项目用 ReAct 式编排做意图→拆单→审批路由→记忆。

### A3. 意图识别怎么做的？准确吗？
- 要点：冷启动用"领域词典 + 动作词"组合匹配（可解释、离线可跑）；生产接大模型做零样本分类，
  并用 SFT 强化；评测用 `evaluate.py`，rule-baseline 离线 acc≈0.975。强调"规则可兜底、模型提上限"。

### A4. 混合检索为什么用 RRF 融合，而不是简单加权？
- 要点：TF-IDF（字面、可解释、零依赖）与 FAISS 向量（语义）是**异构排序**，分值尺度不同，
  直接加权要调权重且不稳；**RRF（Reciprocal Rank Fusion）** 只在"排名"上融合，
  `score=Σ 1/(k+rank)`，无需归一化、对召回源数量鲁棒。本项目离线向量确定性可跑。

### A5. 你们的 Embedding 是怎么来的？为什么能离线跑？
- 要点：默认 `LocalEmbeddingProvider` 用**子词/字符哈希池化**生成确定性稠密向量，
  不依赖外网模型权重，Demo 即开即用；生产可切 sentence-transformers 真语义向量
  （`EMBEDDING_BACKEND=st`）。说明"演示与生产的权衡"。

### A6. 怎么解决大模型幻觉 / 保证可溯源？
- 要点：检索结果**强制带 source**，生成时引用来源；审计场景要求"可回溯、可核查"；
  敏感操作（Ukey 回收、权限调整）强制双人审批。这是 ToB/政务落地刚需。

### A7. 多轮对话 / 记忆怎么实现？
- 要点：Agent 记忆层保留上下文（ReAct 式），按工单维度聚合；拆单后每条审批独立跟踪进度。
  可补充"长期记忆用向量库存摘要、短期用对话窗口"。

### A8. 工单拆单的逻辑是什么？
- 要点：意图识别命中多个服务项 → 生成多条独立子工单，各自路由责任人/时限，进度卡片分节点可视化；
  避免"只办部分、中途补单"。举例："借终端开视频会并联网"→ 终端领用/打印机/联网 三条审批。

### A9. 语音入口怎么做的？
- 要点：ASR 适配层（`asr.py`）适配器模式：`MockASRProvider` 离线演示按音频大小返回意图短语，
  生产接 **FunASR**（已预留）。前端 `voice.html` 录音 → 上传 → 转写 → 喂给 Agent 生成工单。

### A10. 审批流怎么对接真实 OA？MCP 是什么？
- 要点：OA 适配层（`oa_mcp.py`）适配器模式：`MockOAClient` 内存记账演示，`McpOAClient` 预留
  MCP（Model Context Protocol）transport 接真实 OA。MCP 是"模型调用外部系统的标准化协议"，
  让 Agent 以统一方式接工具/系统，避免每家 OA 写一套适配。

### A11. 你们怎么评测效果？
- 要点：离线 `evaluate.py` 给 rule-baseline 验证意图识别 acc≈0.975；检索用命中+来源可核查；
  缓存/量化有显式收益口径。强调"数据-训练-评测闭环"与"没有真实标注就先把可验证基线做扎实"。

### A12. 生产怎么部署？
- 要点：FastAPI + uvicorn，Dockerfile + docker-compose 一键起；Nginx 反代 + HTTPS；
  政务/内网可私有化（量化+蒸馏小模型）。详见 `deploy-guide.md`。

## C. 产品 / 行为面（产品经理岗 & 综合岗重点）
### C1. 这个项目你怎么定义"成功指标"？
- 要点：动作自动化率（一句话→自动拆单覆盖率）、首次解决率、审批平均时长下降、人工补单率下降、
  问答可溯源率 100%、单轮推理成本。强调"指标要可观测"。

### C2. 如果资源只够做一件事，先做哪个？
- 要点：先做"意图识别 + 拆单"（动作链核心），因为它决定后面一切；缓存/量化是成本优化，可后置。
  体现"抓主链路"的产品优先级判断。

### C3. 你和真实业务方（审计/运维）怎么对齐需求？
- 要点：从"高频重复诉求"和"合规可溯源"两个真实痛点切入；用服务目录抽象能力边界；
  用 Demo 快速对齐而非长文档。

### C4. 这个项目你遇到的最大挑战？怎么解决的？
- 要点：选"多意图拆单的准确性"或"可溯源防幻觉"，按"问题→尝试→方案→收益"讲，带复盘。

### C5. 如果让你重做，哪里会不一样？
- 要点：更早做评测闭环、更早接真实 OA/MCP、缓存与量化在架构设计期就预留（其实本项目已预留，可讲"庆幸当初预留了"）。

## E. 高频"陷阱题"应对
- "你这项目是不是套壳/调 API？" → 答：基座可插拔是事实，但**核心资产在编排、检索融合、可溯源与推理加速**，
  这些与用哪家模型无关，是工程与算法沉淀。
- "没有真实数据怎么证明有效？" → 答：用**可验证基线 + 离线评测 + 架构收益口径**，并说明上线后的埋点方案。
- "为什么不用 LangChain？" → 答：自研轻量编排更可控、依赖少、易调试，也更能讲清每一步；
  LangChain 适合快速原型，生产可控性是我们优先考虑的（可补充"不排斥，关键看治理"）。
