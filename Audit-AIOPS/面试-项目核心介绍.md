# Audit-AIOPS · 面试项目核心介绍（可直接讲/直接背）

> 用途：面试时把"审计智能一体化运维平台助手"这个项目讲清楚、讲出技术深度与产品价值。
> 配套：技术深挖见 `面试-题目准备.md`；算法/推理优化专项见 `面试-优化技术面试题库.md`；
> 两份简历见 `简历-AI-Agent开发工程师.md` 与 `简历-大厂产品经理.md`。

---

## 一、一句话定位（电梯演讲，30 秒）

> "我做了一个面向**审计运维场景**的智能一体化助手 Audit-AIOPS：员工用一句话（文字或语音）提诉求，
> 系统用 **Agent 编排**自动完成意图识别、工单拆单、审批路由与进度跟踪；知识问答用
> **混合检索（关键词 + 向量 + RRF 融合）** 保证事实可溯源；底层大模型可插拔
> **混元 / 通义千问**，并用 **缓存复用 / 量化 / 蒸馏** 做推理加速与私有化落地。
> 整套后端 FastAPI、前端政务蓝白原型、Docker 一键部署，已本地全链路跑通。"

---

## 二、为什么做（动机，讲"问题"而不是"技术"）

- **审计运维诉求碎片化**：借终端、开视频会、联网、Ukey、备份…… 往往一句话里藏着多件事，
  传统工单系统要人手动拆、分别找责任人，容易"只办一半、中途补单"。
- **知识散、易出错**：运维手册 / 审计制度分散，人工答易遗漏出处，审计场景要求**可溯源、可合规**。
- **成本与合规**：高频重复问题反复调大模型贵；涉密内网倾向**私有化小模型**而非公网 API。

→ 所以项目目标不是"做个聊天机器人"，而是"把**运维动作链**自动化 + 让回答**可溯源** + 让部署**省成本可合规**"。

## 三、你做了什么（技术架构，画得出这张图）

```
            用户（文字 / 语音 ASR）
                  │
   ┌──────────────▼───────────────┐
   │  Agent 编排层 (orchestrator)  │  意图识别 → 拆单 → 审批路由 → 记忆(ReAct)
   └───┬──────────┬──────────┬────┘
       │          │          │
   ┌───▼───┐  ┌───▼────┐  ┌──▼──────────┐
   │ 服务目录│  │ 知识库  │  │  OA/MCP 审批 │
   │ 拆单   │  │ 混合检索│  │  提交/催办   │
   └───────┘  └───┬────┘  └─────────────┘
                  │  TF-IDF + FAISS + RRF
   ┌──────────────▼───────────────┐
   │  可插拔 LLM 基座（Mock/混元/千问）│
   │  + 应用层 KV/Prompt Cache 加速   │
   └───────────────────────────────┘
   训练侧 SFT(LoRA/QLoRA) · 量化 · 蒸馏 → 私有化小模型
```

**分层（你写的）：**
- `app/config` 配置；`app/models` Pydantic 契约；`app/llm` 可插拔大模型客户端 + 缓存；
- `app/agent` 编排（意图识别 / 记忆）；`app/services` 检索、ASR、OA 适配层；
- `app/api` 路由；`main` 装配；`static` 政务蓝白前端原型（6 个演示页）。

## 四、技术亮点（面试官最爱追的点，每个都能展开）

1. **Agent 编排而非裸 RAG**：一句话多意图 → 自动拆成多条独立审批并分别路由责任人，
   配进度卡片可视化。记忆层用 ReAct 式上下文，支持多轮。
2. **混合检索 + RRF 融合**：TF-IDF 关键词召回（可解释、零依赖）+ FAISS 向量召回（语义），
   用 **Reciprocal Rank Fusion** 融合，兼顾"字面命中"与"语义命中"，且离线可跑（本地确定性向量）。
3. **可溯源回答**：知识问答结果标注来源文档，支撑审计合规与事实核查。
4. **可插拔基座 + 推理加速**：Mock 默认离线跑通；接混元/千问走 OpenAI 兼容接口；
   **应用层 Prompt/Semantic Cache** 复用高频结果（已实现，命中省 ~800ms/次成本归零）；
   训练侧 **QLoRA**、推理侧 **4/8-bit 量化**、**知识蒸馏**压到可私有化小模型（模板已落地）。
5. **语音入口 + OA 真实打通**：ASR 适配层（FunASR 预留）+ OA/MCP 适配层（适配器模式，
   可切真实 OA），审批流从"对话"直达"责任人与截止时间"。
6. **一键部署**：Dockerfile + docker-compose + 启动脚本，政务蓝白前端，演示可点。

## 五、结果 / 量化口径（没有真数据就讲"可验证的设计收益"）

- 混合检索 RRF 在《审批流自动拆分》命中 score 0.0333，来源可列。
- 语义缓存 Demo：相同/近似提示二次命中，单次节省模拟推理耗时 ~799ms、成本降至 0；
  高频 FAQ 场景理论命中率 30%~70%。
- SFT 评测基线：意图识别 rule-baseline 离线 acc=0.975（evaluate.py 验证）。
- 4-bit 量化：7B 模型显存从 ~14GB → ~4~5GB。

> 讲法：不要编造业务指标；讲"**架构带来的可验证收益**" + "**如果上线，预期指标是…**"。

## 七、被追问"最大难点"时怎么答（提前备好）

- 难点1：**一句话多意图的准确拆分** → 用"领域词典 + 动作词"组合匹配做冷启动，
  再用 SFT 强化；规则可解释、模型可兜底。
- 难点2：**回答可溯源、防幻觉** → 检索结果强制带 source，生成时引用，审计可核查。
- 难点3：**成本与私有化** → 缓存复用高频、量化/蒸馏压小模型、路由简单任务走小模型。
- 难点4：**并行开发与零冲突** → 端点按 router 拆分、单例隔离、端口避让，体现工程素养。

## 八、一句话收尾（体现思考深度）

> "这个项目我想清楚了一件事：大模型在 ToB/政务场景落地，**不是比谁模型大，而是比谁的
> '动作链路自动化 + 可溯源 + 成本可控'做得扎实**。Agent 编排解决动作，混合检索解决事实，
> 缓存/量化/蒸馏解决成本和合规——三者缺一不可。"
