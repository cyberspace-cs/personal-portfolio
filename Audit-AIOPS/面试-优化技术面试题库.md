## 1. KV Cache（最关键，必考）

**Q：什么是 KV Cache？为什么能加速？**
- 考点：自回归解码每生成一个 token 都要重算前面所有 token 的 K/V，浪费算力。
- 答：把已算过的 Key/Value 沿序列缓存，后续步只算"新 token"的 Q 与已缓存 K/V 做 attention，
  把每步复杂度从 O(n²) 降到 O(n)，显存换时间。是 decoder-only 推理的基石优化。
- **项目映射**：`app/llm/cache.py` 把"KV 复用"思想落到**应用层**——对相同/近似提示复用整段模型结果
  （PromptCache 精确 + SemanticCache 语义），高频 FAQ 二次命中省 ~800ms/次、成本归零。
  类比讲："服务端的 KV 复用的是 token 级前缀，我们复用的是 prompt 级结果，层级不同但思想一致。"

## 2. 量化 Quantization

**Q：INT8 / 4-bit(NF4) 量化原理？损精度吗？**
- 考点：把 FP16 权重/激活映射到低比特（INT8 / NF4），降显存与带宽、提吞吐。
- 答：INT8 用缩放因子+零点做线性映射，近无损；4-bit NF4 是针对正态分布权重设计的 4 比特数据类型，
  QLoRA 还用"双重量化"对量化常数再量化省显存。精度损失可控，小模型略损、大模型几乎无感。
- **项目映射（真实实测）**：`sft/distill_compress.py` 对学生权重做 **INT8 对称量化（per-channel scale）**，
  实测 **fp32→int8 体积 3.95×、掉点 0.0pt**；学生 INT8 CPU 单样本延迟 ~0.6μs。`_quantize_int8()`：
  `scale = max|W|/127（按列）; q = round(W/scale).clip(-127,127).int8`，反量化 `W'=q·scale`。
- **项目映射（大模型上线模板）**：`sft/quantize.py` —— 4-bit/8-bit 推理部署（`BitsAndBytesConfig`，`load_in_4bit=True`），
  可挂载 SFT 的 LoRA 适配器；`sft/train.py` 训练侧用 QLoRA（4-bit 基座 + LoRA）。口径：7B FP16≈14GB → 4-bit≈4~5GB。
- **易混淆点（必答）**：INT8 是「训练后量化 PTQ」的对称线性映射；NF4 是针对正态权重的 4bit 数据类型，配 QLoRA 用；
  两者层级不同——面试别混为一谈。本项目 INT8 是真跑的，NF4/QLoRA 是大模型上线模板。

## 3. 知识蒸馏 Distillation

**Q：知识蒸馏怎么做？软标签为什么比硬标签有用？**
- 考点：用大模型(教师)的 softmax 概率分布训练小模型(学生)，传"暗知识"。
- 答：损失 = `α·KL(学生‖教师)/T² + (1-α)·CE(学生,真值)`。温度 T 软化概率，放大类别间相对关系
  （暗知识），让学生逼近教师的"判断分布"而非只学硬标签；CE 保硬准确率。适合把重模型能力压到小模型。
- **项目映射（真实实测）**：`sft/distill_compress.py` 在意图识别任务上跑通完整 KD：
  Teacher(dim=8192, acc=100%) 对**全量样本**打软标签(T=3.0) → Student(dim=512) 从**仅 42 条硬标签的 95%**
  提升到 **100%（+5pt）**。损失即 `α·CE(hard)+(1-α)·T²·CE(soft)`，梯度按 T² 缩放（代码 `_train_softmax` 的 `soft_targets` 分支）。
  这正是「标注预算受限 → 教师给未标注数据打软标签（半监督蒸馏）」的经典收益，可当场复现。
- **项目映射（大模型上线模板）**：`sft/distill.py` —— 教师(Qwen-72B/混元) → 学生(Qwen2.5-1.5B/0.5B)，
  把"意图识别/要素抽取"轻任务蒸馏到可私有化小模型。与量化组合成"压缩双拳"。
- **追问「软标签为什么有用」**：硬标签是 one-hot，只说"对/错"；软标签保留类间相对概率（"Ukey制作"与"Ukey调整"更接近），
  这些「暗知识」让小模型学到决策边界的形状，等价于更多监督信号——所以小样本时增益最明显（本项目 +5pt 即证据）。

## 4. 低参微调 LoRA / QLoRA

**Q：LoRA 为什么省资源？和全量微调区别？**
- 考点：只训低秩适配矩阵 A/B，冻结底座 W，ΔW=BA 旁路叠加。
- 答：可训练参数量从 O(d²) 降到 O(r·d)，显存友好、多任务适配器可热插拔并存、不易灾难性遗忘。
  QLoRA = LoRA + 4-bit 量化基座，进一步降显存（单卡 12~16GB 训 7B~13B）。
- **项目映射**：`sft/train.py` 的 `LoraConfig`(r=16, target q/k/v/o)，与量化一体；领域 SFT 数据飞轮见 `dataset.py`/`evaluate.py`。

## 5. 模型剪枝 Pruning

**Q：结构化 vs 非结构化剪枝？剪枝和量化区别？**
- 考点：去掉冗余权重降低算力；剪枝降「非零个数」、量化降「每权重比特数」，二者正交。
- 答：非结构化剪枝置零单权重，压缩率高但需稀疏核/存储才能加速、通用硬件不友好；结构化剪枝去掉整通道/注意力头，
  通用硬件可加速但压缩率受限。常配合微调恢复精度；工程常用「先剪枝再量化」。
- **项目映射（真实实测）**：`sft/prune.py` 对 Student(dim=512) 做**非结构化幅度剪枝**，扫描稀疏度得到真实权衡曲线：
  **98% 稀疏仍 100% acc（拐点）、稀疏存储 1.1KB、理论乘加削减 50×**；99% 掉到 95.5%、99.5%→87.5%、99.9%→44.5%（断崖）。
  实现：`_prune_by_magnitude()` 按 |w| 分位阈值置零。可当场 `python sft/prune.py` 复现，`/api/opt/prune-report` 可查。
- **易混淆点**：剪枝的「稀疏度」不等于量化的「压缩比」——前者是零的比例，后者是比特数下降；本项目二者可叠加（98% 稀疏 + INT8）。

## 6. 推测解码 Speculative Decoding

**Q：推测解码怎么加速又不掉精度？**
- 考点：用小草稿模型并行猜 k 个 token，大模型一次并行验证，命中即接纳多个。
- 答：草稿模型(draft)快速生成候选，目标模型(verifier)用单次前向对候选做接受/拒绝，接受最长一致前缀、
  首个不一致处用 target 纠正，数学上**与自回归等效（无精度损失）**，步数减少、吞吐提升，成本主要在草稿算力。
- **项目映射（真实实测）**：`sft/speculative.py` 用字符级 n-gram 模拟：Target=trigram(更准)、Draft=bigram(更省)、k=4。
  实测 **草稿接受率 39.5%、Target 调用 410→192、加速 2.14×（仅算 Target）/1.42×（计入 Draft 成本）、输出与自回归 100% 一致（无损验证）**。
  可当场 `python sft/speculative.py` 复现，`/api/opt/speculative-report` 可查。
- **追问「为什么无损」**：因为最终每个位置都由 target 的分布决定（草稿只是提议、target 校验/纠正），
  接受的 token 一定是 target 也会产出的 token，所以输出分布不变——本项目实测「输出 100% 一致」即证据。
- **追问「怎么提命中率」**：Draft 越接近 Target 越好——可直接用第 3 节**蒸馏出的小模型**当 Draft，形成技术闭环。

## 7. 批处理与请求路由 Batching / Routing

**Q：continuous batching 是什么？为什么重要？**
- 考点：动态把多请求拼批提升 GPU 利用率。
- 答：传统静态批处理要等长，continuous batching 在序列结束/新增时动态换批，显著提升吞吐、降 P99。
- **项目映射**：可插拔 provider（mock/混元/千问）天然支持"简单意图走小模型/规则、复杂问答走大模型"的
  **路由**；Agent 编排把多意图拆独立事项，天然适合**并行/批处理**。

## 8. 综合/陷阱题

**Q：这些优化怎么排序？先做什么？**
- 答（结合本项目）：**先缓存**（零权重改动、立竿见影、成本归零）→ **量化/蒸馏**（落地私有化、降显存）
  → **剪枝/推测解码**（边际收益、工程成本更高、后置）。强调"收益/成本比"驱动决策。

**Q：缓存会不会返回过期/错误答案？**
- 答：会。对策——对强时效/强一致场景（如实时审批状态）**不缓存或短 TTL**；语义缓存设相似度阈值+
  命中后做一次轻量校验；可观测命中率与"命中后推翻率"。体现工程严谨。

**Q：量化/蒸馏后效果下降怎么验证？**
- 答：用 `evaluate.py` 同口径评测基线 vs 压缩后；看意图识别 acc、检索命中、人工抽样；
  建立"压缩前后对比报告"，不掉到阈值以下才上线。

## 9. 企业级并行（模型 / 流水 / 上下文 / GPU 显存）+ 压缩组合 ⭐核心主线

**Q：推理为什么要并行？模型并行 / 流水并行 / 上下文并行有什么区别？**
- 考点：单卡放不下大模型、并发吃不满 → 四类并行各切不同维。
- 答：
  - **模型并行（张量并行 TP）**：把权重/激活沿张量维（列/行）切到多卡（如 Megatron-LM），每卡算一段、All-Reduce/All-Gather 还原；
  - **流水并行（PP）**：把网络深度切成 stage，micro-batch 流水降低设备空泡；
  - **上下文并行（CP）**：把超长序列的 KV 沿序列维切到多卡，单卡只存 1/N 的 KV（"上下文压缩"的落地）；
  - **数据并行（DP）**：多卡复制、吃更大 batch（与上面正交）。
- **项目映射（概念仿真，真实可复现）**：`sft/parallel.py` 用纯 numpy 讲清前三类——
  **模型并行 8 卡单卡参数比 12.5%（输出与单卡逐元素一致 ✓）、流水并行 4 卡利用率 25%→84%（3.4×）、上下文并行 8 卡单卡 KV 比 12.5%**；
  并组合量化算单卡显存预算：**7B 模型 fp32 单卡 6.8GB → INT8+4×4 并行 1.7GB/卡 → INT4+4×4 0.85GB/卡**。
- **追问「压缩和并行什么关系」**：正交且可叠加——剪枝降非零个数、量化降比特、并行降单卡负载；**标准顺序是压缩在前、并行在后**（模型越小，通信/算力越省，并行越划算）。这正是企业私有化低显存部署的核心。

## 10. 迁移学习：从港大黄超团队(HKUDS) / nanobot 吸收 Agent 哲学

**Q：你做过 Agent，怎么保证它生产级可用？/ 你参考了哪些优秀开源 Agent 设计？**
- 考点：会不会"站在巨人肩膀上"做 Agent，而不只是调 API。
- 答：认真研究过港大黄超团队（HKUDS，LightRAG/RAG-Anything/MiniRAG/AutoAgent/CLI-Anything/OpenSpace）与 **nanobot**，吸收其核心哲学：
  - **Agent = Model + Harness**：把复杂度放进 harness（编排/工具/环境），基座做薄、可插拔；
  - **ReAct 本质**：Reasoning→Action→Observation 的 while 循环，大道至简；
  - **CLI 是 Agent 原生交互**（CLI-Anything）：比 GUI 自动化更稳、更省 token；
  - **skill 进化 > 参数/工作流进化**（OpenSpace）：经验沉淀为可复用 skill，泛化最强；
  - **Token 成本要"自负盈亏"**：追求能力上界时压住成本；
  - **ToB 容错远低于 ToC**：生产级稳定靠双人审批 + Checkpoint 恢复。
- **项目映射**：我们的 orchestrator 已是 ReAct 式；语义/Prompt 缓存 = 成本控制；双人审批 + Checkpoint = ToB 稳定；MCP-native = nanobot 思路；**图 RAG 已落地（见 §11，吸收 LightRAG，作为检索第三路）**；下一步高价值动作是 **prompt cache 强化**、**skill 沉淀**；**多模态 RAG 已落地（见 §12）**。完整迁移映射与 P0/P1/P2 行动项见 `docs/hkuds-transfer-learning.md`。

## 11. 图 RAG 检索增强（LightRAG 思路）⭐检索侧核心升级

**Q：图 RAG 和向量 RAG 有什么区别？为什么需要图？**
- 考点：扁平向量 RAG 只做块级余弦，无法表达实体间关系链；图 RAG 加实体关系结构，沿关系扩散召回。
- 答：向量 RAG 擅长"字面不同但意思近"，不擅长"关系链推理"与"关系相关召回"；图 RAG 先抽实体、建共现图，再让检索沿图扩散，把"同关系簇但未出现查询词面"的关联文档也召回。二者互补，本项目做"关键词+向量+图"三路 RRF 融合。
- **项目映射（真实实测）**：吸收港大黄超团队 **LightRAG** 的「图索引+双层检索」。在 `app/services/retrieval_hybrid.py` 加**审计实体共现图**作为第三路：
  - 实体抽取用审计领域词典（17 实体，替代 LLM 抽取，纯 CPU 可复现），构建 `GraphIndex`（实体→文档、实体→共现邻居，权=共现文档数）；
  - **双层检索**：Low-level（查询实体直接命中）+ High-level（沿图 BFS 扩散 2 跳召回关联实体/文档），标注每条命中的「直接实体」与「图扩散关联实体」；
  - 实测 **17 实体 / 108 边 / 中枢「审批」**，**6/6 查询均有图扩散多召回、平均 +2.33 篇**（如"Ukey 回收"额外召回"数据安全与审计留痕"等关联文档）。
- **追问「实体抽取为什么用词典不用 LLM」**：审计实体封闭、术语规范，词典版召回足够且 100% 可复现、零依赖、可当场演示；LLM 抽取质量更高但需模型、慢、难复现。讲清这个取舍即是加分点。完整见 `docs/graph-rag.md` 与 `/knowledge-hybrid.html`（三列对比第三列）。

## 12. 多模态 RAG（RAG-Anything 思路）+ 单轮 token 成本量化 ⭐已落地

**Q：多模态 RAG 怎么做？为什么审计场景需要？**
- 考点：RAG-Anything 把"文本 + 图 + 表 + 公式"统一进 RAG；审计文档含大量表格（资产台账、权限变更表）与截图（Ukey 制作界面、留痕界面），纯文本 RAG 会漏掉这些结构化 / 视觉信号。
- 答：把每篇文档附带的「表格 / 截图」作为多模态元数据源，和文本一并纳入检索；真实视觉编码由多模态大模型（混元多模态 / 千问-VL）对图像 / 表格做跨模态编码，产出的向量与文本向量统一进同一检索空间。
- **项目映射（真实可复现，诚实标注）**：`retrieval_hybrid.py` 的 `MultimodalRetriever` 把审计领域内置样本（Ukey 制作截图、权限变更审批表、资产台账、审计留痕截图等）作为多模态元数据纳入统一检索；命中时返回 `modalities`（image / table）与 `multimodal_hits`。视觉编码层 `app/services/multimodal_encoder.py` 已做成**可插拔**：默认 `proxy` 复用预撰写描述（= VLM 预期输出代理，零依赖可复现）；配置 `VISION_PROVIDER=hunyuan/qwen` + 密钥后，调用真实多模态大模型对 `assets/screenshots/` 真实截图做视觉理解（真·视觉嵌入），响应统一带 `encoder_mode` 标记、无密钥自动降级，详见 `docs/multimodal.md`（方向 10）。

**Q：怎么量化大模型成本？为什么 ToB 项目必须算这笔账？**
- 考点：黄超强调 Agent 要"自负盈亏"——能力上界要用成本约束。
- 答：把"单轮 token 成本"拆成 输入×输入单价 + 输出×输出单价；自托管小模型按 GPU 时租折算远低于 API 直调；再叠加 量化（体积↓）、投机解码（更少大模型调用）、缓存命中（命中即 0 成本）三道降本。
- **项目映射（呼应黄超成本控制）**：`/api/opt/cost-report` 端点把本项目真实实测的压缩比（×63）、投机加速（×2.14）、接受率（39.5%）与单价 / 缓存命中率假设结合，给出「纯 Teacher(API) → INT8 学生自托管 → 学生+投机+缓存」的单轮成本与月成本对比；实验台 `/optimization.html` §8 提供可交互「降本计算器」。实测：纯 Teacher 单轮 ¥0.042 → INT8 学生 ¥0.00016 → 优化路径 ¥4.9e-5，月调用 500 万次可省约 99.9%。（单价 / 命中率为演示假设，加速 / 压缩比为真实实测）

## 13. Prompt / 前缀 KV-Cache 强化（呼应黄超「成本控制·自负盈亏」）⭐已落地

**Q：prompt cache（前缀缓存）和普通的 response cache 有什么区别？什么场景收益最大？**
- 考点：prompt cache 复用的是**稳定长前缀的 prefill KV**，不是整段对话结果；在"同一份系统提示 + 大量不同用户 query"的场景收益最大（典型如客服 / 审计问答，系统提示含规范、角色、政策文件摘要，长达上千 token）。
- 答：服务端把长稳定前缀的 KV 留在显存，第二次起**跳过前缀重算**，只算 query + 一次极小缓存读取；与"整段响应缓存"是两层——前者省 prefill 算力（KV 级复用），后者省整次推理（结果级复用）。
- **项目映射（真实可复现）**：`sft/prompt_cache.py`（纯 numpy / CPU）仿真审计运维流量：5 业务域 × 2000 请求（zipf 倾斜），同一份系统前缀第二次起命中缓存——
  - **前缀缓存命中率 99.75%**、**节省 token 占全量 92.4%**、**TTFT（首字延迟）下降 87.7%**、月（500 万请求）省约 **¥1,496** prefill 算力。
  - 与 `app/llm/cache.py`（应用层 精确 + 语义 响应缓存）构成**两层缓存架构**：高频 / 近义审计问答成本与首字延迟同时下降。
  - 端点 `GET /api/opt/prompt-cache-report`；实验台 `/optimization.html` §9（命中率 + 省 token + TTFT 下降 + 月省成本 + 累计节省曲线）。诚实标注：prefix/query token 数与单价是演示假设，命中率由流量结构真实仿真。

## 14. Agent 技能中心（OpenSpace「skill 进化」）⭐已落地

**Q：你的 Agent 能力是怎么组织的？为什么不直接写 if-else？**
- 考点：HKUDS / OpenSpace 的"skill 进化"——能力以**可演进的 skill** 沉淀，编排层零改动即可增删 / 升级，而不是硬编码逻辑。
- 答：把 Agent 能力拆成带版本与演进来源的技能（触发意图 / 是否需审批 / 所用工具），新增能力 = 加一条或升一版；审批类技能与"双人审批 + Checkpoint"对齐，保证 ToB 安全。
- **项目映射（真实可复现）**：`app/skills/registry.py` 领域技能注册表（9 技能：审批路由 / 工单拆单 / 知识问答 / 监控告警 / 服务目录导航 / 工单推进 / 审计留痕 / 语音入口 / OA-CLI 原生工具），每技能含触发意图、是否需双人审批、工具、版本与演进来源。`AgentOrchestrator` 经 `resolve_skills(text)` 把用户输入实时映射为技能并写入记忆——**增删 / 演进能力零改动编排逻辑**；`knowledge_qa` 的 `evolved_from` 直观记录"关键词检索 v1.0 → 混合 RAG v1.1 → 图+多模态 RAG v1.3"。端点 `GET /api/skills`、演示页 `/agent-demo.html` 技能中心面板。详见 `docs/skills.md`。

## 15. 多模态 RAG 接真实视觉编码（混元视觉 / 千问-VL 可插拔）⭐已落地（方向 10）

**Q：你说多模态 RAG 用了描述文本代理，那真实视觉嵌入怎么接？不会是"假的多模态"吧？**
- 考点：诚实区分"代理可复现"与"接真实视觉模型"，且架构要让生产切换零成本。
- 答：视觉编码层我做成**可插拔三态**——`ProxyVisualEncoder`（零依赖，复用预撰写描述，等价于 VLM 预期输出）/`HunyuanVisionEncoder`/`QwenVisionEncoder`（env 门控调真实多模态大模型对真实截图做视觉理解，产出实时 caption 替换代理描述）。用 RAG-Anything 的「多模态 → 文本」路径：截图/表格先转文本，再进统一 RAG，无需另建多模态向量库。
- **项目映射（真实可复现 + 可生产）**：
  - 复用 `HUNYUAN_API_KEY`/`QWEN_API_KEY`（与文本 LLM 同密钥），`VISION_PROVIDER=hunyuan/qwen` 即激活；视觉模型名可由 `VISION_MODEL` 覆盖（默认 `hunyuan-vision` / `qwen-vl-max`）。
  - **优雅降级**：无密钥 / 缺真实截图 / 真实调用失败时一律回退 proxy 并在响应标 `encoder_mode`，服务不中断、诚实可讲。
  - `MultimodalRetriever` 每图经 `encode_image(path, cap)` 取描述（proxy=预撰写 / real=VLM 实时）再跨模态打分；端点 `GET /api/knowledge/multimodal-encoder-status` 暴露当前模式与可用 provider；演示页 `/knowledge-hybrid.html` 多模态区块展示 `encoder_mode` 徽标。
  - 真实截图放入 `assets/screenshots/`（按文档标题命名）即激活，无需改代码。
- 讲法收口：「代理模式保证零依赖可复现、面试可当场跑；生产补真实截图 + 配密钥即真·视觉嵌入，架构上把 RAG-Anything 的『多模态→文本』路径完整落地。」

## 16. CLI-native OA 工具层（CLI-Anything 思路）⭐已落地（方向 11）

**Q：你把外部系统（如 OA）接进 Agent，为什么不用 GUI 自动化？**
- 考点：HKUDS / CLI-Anything 的"CLI 是 Agent 原生接口"——GUI 自动化靠元素定位、随改版失效、token 贵、难审计；CLI 命令契约稳定、极省 token、天然可记录回放。
- 答：我把 OA 的审批/工单/目录/告警都先定义成一条条 CLI 命令（如 `oa approval submit --type ukey --applicant 张三 --owner 李工`），Agent 像在终端敲命令一样原生驱动 OA；命令模板既给编排层精确调用，也能直接回显给用户。背后由 OA-MCP 适配层（MockOAClient / McpOAClient）执行，部署时绑定真实 OA 的 MCP server 即可，业务代码与命令契约不变。
- **项目映射（真实可复现）**：`app/services/oa_mcp.py` 的 `OA_TOOLS` 注册表（6 个 CLI 式工具：`oa_approval_submit`/`_query`/`_approve`、`oa_workorder_advance`、`oa_catalog_list`、`oa_alert_raise`），每个带结构化 schema + `cli` 命令模板；`call_oa_tool(name,args)` 即一次 CLI 调用。`app/skills/registry.py` 新增 `oa_cli` 技能（演进来源 `CLI-Anything（HKUDS）`），其 `tools` 直接引用 6 个 OA 工具；编排层 `resolve_skills()` 命中后即可原生调用。端点 `GET /api/tools`、`POST /api/tools/invoke`；演示页 `/agent-demo.html`「⌨️ OA-CLI 原生工具」面板支持实时调用。详见 `docs/cli-native.md`。
- 讲法收口：「ToB 场景里，把外部系统接进 Agent 的正确姿势不是 GUI 自动化，而是给它一个 CLI 原生接口——不稳、不省 token、不可审计的活儿我不干。」
