> **关联文档**：`docs/技术架构方案.md`（开发工程师）、`docs/代码审查报告.md`（审查工程师）、`docs/测试报告.md`（测试工程师）、`docs/项目设计与数据库方案.md`（历史方案）
> **一句话定位**：面向考研 / 考公 / 大厂面试三类人群的 AI 刷题陪练，支持匿名「体验模式」直接可用，登录后获得个性化数据与 AI 能力。

## 0. 文档使用说明

本需求文档是**多角色开发工作流（PM → 开发 → 审查 → 迭代 → 测试）**的第一阶段产出，用于：

1. 明确现有模块的功能边界，避免本期改动「越界」或回归既有体验；
2. 把用户提出的四个新方向（浅色/深色模式、题库自动化长期更新、数据库架构、AI 学习计划）拆解为**功能边界 + 用户故事 + 验收标准**；
3. 为后续《技术架构方案》提供「做什么」的输入，为《测试报告》提供「如何算通过」的判据。

**核心产品原则（贯穿全篇，不可违背）**：
> 匿名用户默认可**看到并使用**核心演示能力（体验模式）；登录后获得**更多**（个性化数据持久化、错题本、打卡、AI 学习计划等）。任何改动不得把演示能力重新锁回登录墙后。

## 1. 产品概述

### 1.1 产品定位
「专属刷题教练」是一个 Web 端（单文件 SPA `coach.html` + FastAPI 后端）的备考刷题工具。它把「题库练习 + 数据看板 + AI 讲解/出题/报告」整合在一个轻量产品里，主打**低门槛体验 + 强个性化**。

### 1.2 目标用户
| 用户群 | 代表场景 | 核心诉求 |
|---|---|---|
| 考研学生 | 数学/英语/政治/专业课刷题 | 按知识点查漏补缺、错题回顾 |
| 考公考生 | 行测/申论/常识刷题 | 题型专项、限时模拟 |
| 求职面试者 | 大厂算法/八股/系统设计 | 高频考点、快速过题 |
| 浏览者（潜在用户） | 朋友/评审/访客点开链接 | 不注册也能感受产品价值 |

### 1.3 设计基调
- 视觉：科技感、简洁、政务/教育蓝白基调（PC 优先，兼顾移动端自适应）。
- 交互：单页多视图（首页 / 刷题 / 模拟考场 / 数据 / 推荐 / 报告），导航即时切换。
- 主题：本期新增**浅色 + 深色双模式**（见 3.1）。

## 2. 现有功能模块盘点（功能边界 + 用户故事）

> 以下模块的边界必须在本期工作中保持不变或被显式重写；任何改动需在《技术架构方案》中标注影响范围。

### 2.1 刷题练习（Quiz）
- **功能边界（做什么）**：按分类（考研/考公/大厂）抽题、单选/多选/判断作答、即时判分、查看解析。
  **不做什么**：不做跨分类混合卷（归属模拟考场）、不做付费/权限题。
- **关键接口**：`GET /api/questions`（可带 `cat` 过滤）、`POST /api/quiz/check`（匿名可用，返回判分）、`GET /api/questions/meta`（公开，题库统计）。
- **用户故事**：
  - US-Q1：作为考研生，我想按「考研」分类刷题，以便集中在考研范围内练习。
  - US-Q2：作为匿名访客，我想不登录也能做几道题并看到对错与解析，以便快速判断产品是否适合我。

### 2.2 模拟考场（Exam）
- **功能边界**：限时、固定题量、交卷后统一判分与用时统计；与日常练习区分（不即时逐题判分）。
- **关键接口**：`POST /api/exam/record`、`GET /api/exam/records/{user_id}`。
- **用户故事**：US-E1：作为考公考生，我想做一次 20 题限时模考，以便评估临场节奏。

### 2.3 学习数据中心（Data / 看板）
- **功能边界**：展示正确率走势、分类占比、能力雷达、连续打卡等聚合视图；登录用户读真实数据，匿名用户读「演示样本」数据。
- **关键接口**：`GET /api/mastery/{user_id}`（知识点掌握度，是 AI 学习计划的关键输入）、`GET /api/quiz/history/{user_id}`、`GET /api/streak/{user_id}`。
- **用户故事**：US-D1：作为登录用户，我想在看板看到近 7 天正确率趋势，以便感知进步。

### 2.4 智能推荐（Recommendation）
- **功能边界**：基于薄弱知识点/错题，推荐下一批题目；匿名用户基于题库总体分布给「示例推荐」。
- **用户故事**：US-R1：作为用户，我想系统自动把我的薄弱知识点排到前面，以便优先攻克。

### 2.5 AI 押题报告（Report）
- **功能边界**：综合近期练习生成「押题 + 薄弱点 + 建议」报告；由 LLM 生成，含降级文案兜底。
- **关键接口**：`POST /api/report`。
- **用户故事**：US-P1：作为备考用户，我想在考前得到一份押题报告，以便聚焦高频易错点。

### 2.6 错题本（Wrong Book）
- **功能边界**：自动归集答错题目，记录错误次数，支持再次练习；**登录用户持久化**。
- **关键接口**：`POST /api/wrong-book`、`GET /api/wrong-book/{user_id}`。
- **用户故事**：US-W1：作为用户，我想把反复做错的题集中复习，以便考前精准打击。

### 2.7 打卡 / 连续学习（Streak）
- **功能边界**：每日打卡，记录连续天数；驱动数据看板的「连续学习」卡片。
- **关键接口**：`POST /api/checkin/{user_id}`、`GET /api/streak/{user_id}`。
- **用户故事**：US-S1：作为用户，我想用连续打卡维持学习惯性，以便形成习惯。

### 2.8 体验模式（Experience Mode，匿名可用）
- **功能边界**：未登录时，首页/刷题/模考/数据/推荐/报告均以「演示数据 + 匿名判分」形式可用；不写任何个人持久化数据（写入 `user_id=None` 的演示分支或纯前端样本）。
- **关键实现**：前端 `updateDemoBanner()` 浮层提示「体验模式」；后端 `/api/quiz/check` 等接口支持 `user_id=None`。
- **用户故事**：US-X1：作为访客，我打开链接就能看到完整产品形态，不必先注册。

### 2.9 AI 答疑 / 出题 / 对话（Agent 能力）
- **功能边界**：针对题目做 AI 深度讲解、按知识点生成新题、自由问答；由 `server/agent/` 多智能体模块 + `_structured_llm` 支撑，含本地降级兜底。
- **关键接口**：`POST /api/explain`、`POST /api/gen`、`POST /api/chat`。
- **用户故事**：US-A1：作为用户，我想就某道错题追问「为什么」，以便真正理解而非背答案。

## 3. 本期新增方向（四大方向）

### 3.1 方向一：浅色 / 深色模式（主题系统）

#### 3.1.1 背景与痛点
当前 `coach.html` 的 `:root` 仅定义浅色变量（背景 `#f5f7fb`、墨色 `#1a2340` 等），**无 `data-theme`、无 `prefers-color-scheme`、无深色变量**。在夜间 / 低光环境、OLED 设备上体验差，且不利于评审与差异化展示。

#### 3.1.2 功能边界
- **做什么**：
  - 在 `:root` 基础上新增 `[data-theme="dark"]` 深色变量集（同名字、深色值），保持全部 CSS 用 `var(--x)` 引用（现状已满足，无需改样式规则，只补变量）。
  - 提供主题切换入口（导航栏图标按钮），三态：**浅色 / 深色 / 跟随系统**。
  - 用户选择持久化到 `localStorage`；首次访问读取系统 `prefers-color-scheme` 作为默认。
  - 切换即时生效，无闪烁（在 `<head>` 早期内联脚本应用主题，避免 FOUC）。
- **不做什么**：不做按页面/按视图独立主题；不引入主题社区/自定义配色（超出本期）。

#### 3.1.3 用户故事
- US-LD1：作为夜间学习者，我想切到深色模式，以便保护视力。
- US-LD2：作为懒得设置的用户，我想「跟随系统」，以便昼夜自动切换。
- US-LD3：作为回头用户，我想刷新后仍保持上次选择，以便不被重置。

#### 3.1.4 功能需求
- FR-LD1：主题状态枚举 `{light, dark, system}`，默认 `system`。
- FR-LD2：`<head>` 内联脚本在解析 CSS 前读取 `localStorage.theme` 与 `matchMedia`，设置 `<html data-theme>`。
- FR-LD3：切换按钮在浅色/深色/系统三态间循环，文案与图标同步。
- FR-LD4：`system` 态下监听 `matchMedia('(prefers-color-scheme: dark)')` 变化并实时切换。
- FR-LD5：深色变量需保证正文对比度 ≥ WCAG AA（4.5:1），图表（Chart.js）配色同步适配。

#### 3.1.5 验收标准（AC-LD）
- AC-LD1：默认访问时，系统为深色则页面为深色，反之浅色。
- AC-LD2：点击切换后，所有视图（含图表、卡片、弹层、登录框）颜色随主题变化，无「漏网」的硬编码浅色背景。
- AC-LD3：刷新后主题保持；`system` 态下操作系统切换深色/浅色，页面在 1 秒内跟随。
- AC-LD4：体验模式浮层、移动端布局在两种主题下均正常。

### 3.2 方向二：题库自动化长期更新

#### 3.2.1 背景与痛点
当前题库由 `server/gen_questions.py` 静态生成 `server/data/questions.json`（v2，86 题），属「一次性脚本」。长期竞赛展示与真实运营需要**题库可持续增长、可溯源版本、可自动校验质量**，避免人工每次手动改代码。

#### 3.2.2 功能边界
- **做什么**：
  - 把题库生成长为**可版本化的数据资产**：`questions.json` 增加 `version`、`generated_at`、`count`、`sources`、`checksum` 等元信息（现状已有 `version/generated_at/count`，需补 `sources/checksum`）。
  - 提供**题库版本表** `question_bank_versions`（见 3.3），记录每次更新的版本号、题量、来源、时间、状态（draft/published）。
  - 提供**长期自动化规划**：通过定时任务（cron / 平台自动化）周期性运行「增量生成 + 校验 + 入库」流程，增量追加新来源/新题，不破坏既有题的 `id` 稳定性。
  - 质量校验内置：答案下标越界、重复题干、选项数合规、知识点非空等。
- **不做什么**：不做「AI 全自动爬虫抓取外部题库」（合规与版权风险，超出本期）；不做付费题库接入。

#### 3.2.3 用户故事
- US-QB1：作为维护者，我想每月自动补充一批新题，以便题库持续增长而不必手工改代码。
- US-QB2：作为维护者，我想每次更新都有版本记录与校验报告，以便出问题可回滚。
- US-QB3：作为用户，我想在不同时段都能刷到「最新题库」，以便练习内容不过时。

#### 3.2.4 功能需求
- FR-QB1：`gen_questions.py` 支持「增量模式」——读取现有 `questions.json`，合并 `EXTRA`/`NEW` 增量池，保留已存在题 `id`，追加新题并重新分配 `id`。
- FR-QB2：生成后写入版本元数据并在 `question_bank_versions` 落一条 `draft` 记录；校验通过且人工/自动确认后置为 `published`。
- FR-QB3：内置校验器，失败则非零退出并输出问题行清单，阻断入库。
- FR-QB4：定时任务编排：每周/每月触发生成→校验→（自动）入库→更新 `meta` 接口缓存。
- FR-QB5：`GET /api/questions/meta` 返回当前 `version`、`count`、`sources`、`generated_at`，供前端展示「题库版本」。

#### 3.2.5 长期自动化规划（示意节奏）
| 频率 | 动作 | 产出 |
|---|---|---|
| 每周 | 运行增量生成 + 校验 | 候选 `draft` 版本、校验报告 |
| 每月 | 评审并 `publish` 通过校验的候选版本 | 线上题库 +1 版本、用户可见新题 |
| 每季度 | 复盘来源覆盖度（考研/考公/大厂比例、知识点均衡） | 来源补充清单，指导下一季度增量池 |

#### 3.2.6 验收标准（AC-QB）
- AC-QB1：运行生成脚本后，`questions.json` 含 `checksum` 且可与历史比对；增量模式不改动既有题 `id`。
- AC-QB2：校验失败明确报错并退出，不会写入损坏数据。
- AC-QB3：新增 `published` 版本后，`/api/questions/meta` 的 `version/count` 同步更新。
- AC-QB4：定时任务可在隔离环境跑通「生成→校验→入库」全链路（测试阶段用一次性/手动触发验证）。

### 3.3 方向三：数据库架构升级

#### 3.3.1 背景与痛点
现有 `database.py` 仅 6 张表（`questions/users/quiz_records/wrong_book/daily_streaks/exam_records`），均为 SQLite，`user_id` 强约束 `NOT NULL`。本期引入**学习计划**与**题库版本**两类新实体，且需为后续可能的 PostgreSQL 迁移预留路径。

#### 3.3.2 功能边界
- **做什么**：
  - 新增 `study_plans` 表：存储 AI 生成的周/阶段学习计划（用户、周期、目标分类、每日任务 JSON、生成时间、是否当前生效）。
  - 新增 `question_bank_versions` 表：题库版本元数据（版本号、题量、来源、摘要、状态、时间）。
  - 为高频查询补索引（如 `wrong_book(question_id)`、`quiz_records(created_at)`、`study_plans(user_id, active)`）。
  - 保持向后兼容：`init_db()` 用 `CREATE TABLE IF NOT EXISTS`，老库升级只追加不删改。
  - 抽象一层 DB 访问（或至少把 `DB_PATH`/`PRAGMA` 集中），便于将来切 PostgreSQL（本期仍 SQLite，仅留迁移说明）。
- **不做什么**：本期**不实际迁移到 PostgreSQL**（仅提供 DDL 兼容说明与切换点），不做分库分表。

#### 3.3.3 用户故事
- US-DB1：作为用户，我想系统根据我的薄弱点生成一份学习计划并保存，以便每日照做。
- US-DB2：作为维护者，我想题库每次更新都被记录，以便审计与回滚。
- US-DB3：作为开发者，我想将来能平滑切到更稳的数据库，以便支撑更大用户量。

#### 3.3.4 功能需求
- FR-DB1：`study_plans(user_id, cat, plan_json, week_start, is_active, created_at)`，同一用户仅一条 `is_active=1`。
- FR-DB2：`question_bank_versions(version, count, sources_json, summary, status, created_at, checksum)`。
- FR-DB3：补充索引，并在 `init_db()` 中以 `IF NOT EXISTS` 幂等创建。
- FR-DB4：提供 `migrations` 兼容说明文档（DDL 同时给 SQLite 与 PostgreSQL 等价写法）。

#### 3.3.5 验收标准（AC-DB）
- AC-DB1：在既有 `coach.db` 上运行 `init_db()`，新表被创建，旧表数据不丢。
- AC-DB2：`study_plans` 写入/读取/「仅保留一条活跃」逻辑正确。
- AC-DB3：索引在 `EXPLAIN QUERY PLAN` 中对典型查询生效。
- AC-DB4：提供 PostgreSQL 等价 DDL，关键差异（自增、JSON 类型、PRAGMA）有注释。

### 3.4 方向四：AI 学习计划

#### 3.4.1 背景与痛点
现有产品能「诊断薄弱点」（`/api/mastery`）和「出报告」（`/api/report`），但**缺少把结果转成可执行日程**的闭环。用户刷完题仍不知道「明天该刷什么、刷多少」。

#### 3.4.2 功能边界
- **做什么**：
  - 新增 `POST /api/study-plan`：输入 `user_id`（或匿名 `None` 给示例）、目标分类、周期（如 7 天），结合 `mastery`、近期 `quiz_records`、`wrong_book`、`streak`，由 LLM 生成结构化周计划（每日主题 + 题量 + 重点知识点 + 小贴士）。
  - 新增前端「学习计划」视图（在导航中加入入口），渲染计划卡片/日历；登录用户可「保存并设为当前计划」（写 `study_plans`），匿名用户仅预览。
  - LLM 失败时用本地降级模板（按薄弱知识点占位）保证可用。
- **不做什么**：不做自动定时推送消息（超出前端范围）；不做与日历 App 的双向同步。

#### 3.4.3 用户故事
- US-SP1：作为登录用户，我想根据我的薄弱点生成一份「未来 7 天每天刷什么」的计划，以便有节奏地备考。
- US-SP2：作为登录用户，我想保存计划并在下次打开时看到它，以便持续执行。
- US-SP3：作为匿名访客，我想先预览一份示例计划，以便决定是否注册获得个性化版。

#### 3.4.4 功能需求
- FR-SP1：计划结构化为 `{week_start, days:[{day, theme, topics:[], count, tip}]}`，由 `_structured_llm` 按 schema 输出。
- FR-SP2：匿名请求返回基于题库总体分布的示例计划（不读个人数据）。
- FR-SP3：保存时 `UPSERT` 当前用户 `is_active=1` 的那条 `study_plans`。
- FR-SP4：`GET /api/study-plan/{user_id}` 读取当前活跃计划供前端呈现。
- FR-SP5：降级：LLM 不可用时用「按 mastery 升序取 Top-N 知识点铺满 7 天」的确定性模板。

#### 3.4.5 验收标准（AC-SP）
- AC-SP1：登录用户生成计划后，`study_plans` 出现一条 `is_active=1` 记录，重复生成仅更新不重复插入。
- AC-SP2：前端学习计划视图正确渲染每日卡片；匿名预览不报错。
- AC-SP3：LLM 故障时返回降级计划（HTTP 200，含 `fallback:true` 标记）。
- AC-SP4：计划所用「薄弱知识点」与 `/api/mastery` 输出一致。

```
刷题教练（SPA）

├─ 打卡 Streak          （登录持久化）
├─ 学习计划 Plan 〔新增〕（登录保存 / 匿名预览）
└─ 主题切换 〔新增〕     （全局：浅/深/跟随系统，localStorage）

questions / meta / quiz/check / register / login / quiz/record / wrong-book
```

## 6. 成功指标（KPI）

- **主题**：双模式切换成功率 100%，两种主题下关键视图无硬编码浅色背景。
- **题库自动化**：从「手动脚本」到「可版本化 + 可定时」；首次自动增量更新题量 +≥10 且 `id` 稳定。
- **数据库**：新表上线后老数据零丢失；活跃计划唯一约束生效。
- **AI 计划**：登录用户生成→保存→再次读取闭环可用；LLM 故障降级率 100% 兜底成功。
- **体验模式不回归**：匿名全流程仍可走通（与阶段 3 审查、阶段 5 测试双重确认）。

## 7. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| 深色变量遗漏导致部分组件「白底黑字」刺眼 | 体验降级 | 审查阶段用双主题截图比对（AC-LD2） |
| 题库增量破坏既有 `id` | 用户进度错乱 | 增量模式只读合并、保留旧 `id`（FR-QB1） |
| LLM 不可用导致计划空白 | 功能不可用 | 确定性降级模板（FR-SP5） |
| 数据库升级丢数据 | 严重 | `IF NOT EXISTS` 幂等 + 升级前备份（AC-DB1） |
| 体验模式因新功能被重新锁登录 | 违背核心原则 | 阶段 3/5 专门核查匿名可用路径 |
